# 17. 图片元数据方向与评星专项

> 关联：`doc/架构设计/06_图片预览模块.md` §6.7（设计）、`PLAN_image_meta.md`（实施计划）、`src/meta.rs`（EXIF 读写纯函数）。
> 状态：P1+P2 已落地；2026-11-23 评级子系统重构落地（分格式真相矩阵 + 延迟批量写，见 17.7——17.6 的两级优化被其取代）。

## 17.1 需求与定版结论

- 手机拍摄图片显示方向不对 → 解码链读 EXIF Orientation（tag 274）自动矫正，八值穷尽变换；
- 用户旋转 **R 单键顺时针**（Q/E 双键被否决："太浪费"）；**0 键清除评级被否决**
  （0 已被 100% 缩放占用）→ Q 清星，1-5 定星；
- 方向**写回 EXIF Orientation（tag 274，正式标准，主流同样写 EXIF）**；
  评级**只写 sidecar `.xmp`（不碰原文件字节，2026-11-22 用户定版）**；
  两者均不存本地配置；筛选删除仅目录模式，不处理压缩包。

## 17.2 生态事实（选型依据）

| 事实 | 结论 |
|---|---|
| Windows 资源管理器星级读取 | 优先 EXIF 18246 Rating + 18249 RatingPercent（Microsoft 扩展）**是向下兼容存量照片的务实策略，非主流写法**（2026-11-22 用户调研修正）；主流 Lightroom/digiKam/XnView 写 XMP xmp:Rating |
| XMP 评级写入形态 | **sidecar `.xmp` 定版**（用户裁定）：Lightroom 约定 `IMG_1234.jpg → IMG_1234.xmp`（with_extension）；嵌入式 XMP 被否决——little_exif 0.6.23 **不支持写 XMP**（xmp.rs 仅内部 EXIF 过滤辅助），自写 JPEG APP1/PNG iTXt 注入代码有写坏文件风险，xmp-toolkit 需 Adobe C++ 工具链 |
| 评级真相链 | 写入只走 sidecar（原文件字节零改动，GIF/BMP/RAW 全格式统一）；读取 sidecar > 嵌入式 XMP（文件头 512KB 搜索 xmp:Rating）> EXIF 18246/18249 存量 |
| kamadak-exif 0.6 | 只读；`Reader::read_from_container(&mut Cursor::new(buf))` 支持内存 buffer——zip 流路径零额外 IO 必需；`get_uint(0)` 返回 `Option<u32>` |
| little_exif 0.6 | 写 **EXIF**（方向 tag 274 用）；`Metadata::new_from_path` → `set_tag` → `write_to_file` 保留其余 tag；**值参数是 `Vec<u16>`**；自定义 tag `ExifTag::UnknownINT16U(vec![v], tag_id, ExifTagGroup::GENERIC)`，组枚举在 `little_exif::ifd::ExifTagGroup` |
| 写出形态全格式核查（2026-11-22） | JPEG=APP1 `Exif\0\0` ✅ / TIFF=原生 IFD ✅ / WebP=`EXIF` RIFF 块（容器规范位置，仅 lossless/extended 可写）✅ / **PNG=库只产 zTXt "Raw profile type exif"（ImageMagick 旧形态）❌**——PNG 标准（ext 1.5）/Windows/kamadak 读链都只认 eXIf 块，库读写不对称 |
| PNG 方向写回 | **绕开库**自实现 `write_png_orientation`：little_exif 读全量元数据（其读链认 eXIf 块与 zTXt 两形态）→ set_tag → `encode()` 产出标准 TIFF blob（即 eXIf 合法 payload）→ 自写 chunk 级替换（CRC32=crc32fast ISO_HDLC，新 eXIf 插 IHDR 后、旧 eXIf 全丢弃） |
| little_exif 无元数据文件坑 | `new_from_path` 对无任何元数据段的文件（image crate 产出的 PNG 无 eXIf）报 `"No metadata found!"`，**与文档注释"解码失败返回空对象"不符**——回退 `Metadata::new()` 空起步再写 |
| 写回往返矩阵测试 | `meta::tests::全格式方向写回往返诊断`：jpg/jpeg/png/tif/webp 全格式 写→读→二次写（覆盖既有 EXIF）→ image::open 解码完整性断言 |
| trash crate 5 | `trash::delete(path)` 进回收站；sidecar 随图连带删除（不存在跳过） |

## 17.3 核心方案：旋转不重写像素

只改 EXIF Orientation tag，显示 = T(tag) 变换，位图不动：

- 写回只动几百字节元数据段，安全快；
- 显示与元数据永不漂移（写回成功 ⇒ invalidate_full 重解码）；
- 方向链轮进推导 `T(o') = Rot ∘ T(o)`：CW 表 1→6→3→8→1（2↔7、4↔5），
  单测"4 次轮转回原值 + 与 apply_orientation 逐点自洽"双验证。

## 17.4 关键决策与教训

1. **删除用标记集，不物理移除 entries**（架构级否决了 PLAN 初稿的"从 entries 移除"）：
   ImgKey=(archive_id, entry_idx)、评级表、多选、锚点全按 entry_idx 寻址，
   物理移除 ⇒ 后续下标整体位移 ⇒ 缓存纹理错位指向错误文件。`ArchiveState.deleted:
   HashSet<usize>` 只在 rebuild_view 谓词剔除，语义等价且零位移风险；
1a. **删除入口 = 选中集 + 右键菜单**（2026-11-22 二次定版，替代初版"筛选条删除
   按钮 + 按全量筛选集删除"）：筛选条改下拉收窄 UI 宽度后，删除复用右键菜单
   「删除选中（进回收站）」/ Ctrl+Delete 按选中集执行——典型流：筛 ≥n → Ctrl+A →
   删除；**切换筛选即清空选中 + 评级变化剔除退出筛选集的选中项**（防不可见旧
   选中被误删）；
2. **invalidate_full（含 natives）**：旋转写回改变了文件方向语义，旧原图（已按旧方向
   矫正）不能再供探针/full/对比度重建三消费者复用，全部清掉重解码；评级写回不动像素，
   不失效任何缓存；
3. **评级字段与显示缓存分离**：ratings 表（会话）合并后台扫描时 `entry().or_insert()`
   ——会话值优先，用户扫描期间手动评的星不被覆盖；
4. **筛选谓词扫描未完成时暂不生效**：ratingscan 线程一次性回传（无渐进消息），
   合并后才让星级谓词生效 + 重建视图——防扫描中途列表反复闪变；
5. **EXIF 评分是"非正式"位（用户调研一票修正）**：18246/18249 为 Microsoft
   扩展，Windows 保留读取只是向下兼容存量；主流写 XMP——初版把评级写进 EXIF
   被用户推翻改 sidecar。**教训：向"生态怎么写"看齐而非"某平台怎么读"**；
   sidecar 附带收益 = 原文件字节零改动 + 评级能力扩展到无 EXIF 容器格式
   （GIF/BMP/RAW 全覆盖，此前 meta_writable 只覆盖 jpg/png/tif/webp）；
6. **Cargo.toml 版本记忆坑**：kamadak-exif 凭记忆写 0.19（不存在），crates.io 实际
   最新 0.6.x——第三方 crate 版本一律先查证再落笔；
7. **同文件并行 Edit 竞态再次踩中**：4 个 Edit 分两文件并行（每文件各 2 个），
   后写覆盖先写部分静默丢失（Edit 结果快照显示成功但实际内容回退）——同一文件的
   多处修改必须逐条串行，逐个验证后继续；
8. **PNG 方向写回链两连坑（2026-11-22 用户实测报出）**：①无元数据 PNG
   `new_from_path` 直接报错（见上表）；②库写 PNG 产 zTXt 旧形态，
   "写成功"但 Windows/读链谁也读不到，重开 app 方向即丢——**库的读写
   能力必须分开核查**（读支持 ≠ 写同形态），写出位置只认容器规范；
9. **测试临时目录并行竞态**：sidecar 测试收尾 `remove_dir_all` 删掉整个共享
   目录，把并行矩阵测试的文件一起删了（"找不到文件"报错误导定位）——并行
   测试各自独立临时目录，共享目录禁 whole-dir 清理。

## 17.6 评级扫描 IO 优化（2026-11-23）

**审计结论**：解码链（方向，压缩包路径零额外 IO / 目录路径 1 次头部读）与
写回链（sidecar 单写）无 IO 问题；放大点只在 `ratingscan`——每张未评级图
三级全跑 = **3 次文件打开 + ≤512KB 头部读**，其中嵌入式 XMP 对相机 RAW
基本纯浪费（XMP 为 TIFF tag 在缩略图数据之后，头部 512KB 文本搜索落空）。
万级未评级图目录 ≈ 3 万次打开 + ~5GB 累计读（HDD 上 40~50s，SSD 3~5s）。

**两项改造**（均收敛在 `meta.rs` 单文件 + `open.rs` 调用点）：

1. **一次头部读双解析**：`read_rating_path(path, embedded_xmp)` 取代原
   三函数链（sidecar → 嵌入式 XMP 整开 → EXIF 整开）。头部 ≤512KB 读一次，
   `parse_xmp_rating` 与 `read_meta_bytes`（kamadak Cursor 源）共用同一
   buffer——JPEG APP1 / PNG eXIf / TIFF IFD0 均在文件头部，头部解析命中
   率等同整文件读；截断致容器解析失败时回退 `read_meta_path` 整文件读。
   未评级图 **3 开 → 2 开**（sidecar 探测无法合并——它是独立文件）；
2. **嵌入式 XMP 探测改配置开关**：`[media] rating_embedded_xmp_enable`
   **默认 false**（兼容模式，用户裁定——多数目录的图都没有嵌入式 XMP，
   探测是纯开销）。默认关后每张未评级图省一次 ≤512KB 头部读 = 扫描耗时
   主导项；开启时相机 RAW 家族（`imgview::is_raw_photo_ext`，改 pub(crate)
   供 open.rs 复用）仍跳过。**生效时机 = 打开目录**（扫描线程 spawn 时
   捕获 bool，热重载不重放扫描）。EXIF 存量读是三级优先的第三级省不掉
   （扫描只需评级不需方向，方向是解码链的事）。

**验证**：新增 `read_rating_path_三级优先与开关` 测试——仅嵌入式 XMP 伪图
（开关 false=None / true=命中）、little_exif 自定义 tag 18246 写 jpg 后
**头部读**解析命中（覆盖截断风险外的主路径）、sidecar 覆盖 EXIF 存量；
`cargo test meta::` 8 项全绿。

> **已被 17.7 取代**：两项优化（read_rating_path / rating_embedded_xmp_enable
> 开关）在 2026-11-23 评级重构中被矩阵层整体替换——`read_rating_path` 删除、
> 开关删键，EXIF 存量读彻底移除，见下节。

## 17.7 评级子系统重构：分格式真相矩阵 + 延迟批量写（2026-11-23）

**定版**（用户推翻 17.6 兼容开关路线，"学习成熟软件生态"）：

| 格式 | 评级存储 | 说明 |
|---|---|---|
| jpg/jpeg/jpe/png/webp | **嵌入式 XMP**（xmp:Rating） | 主流写法；img-parts 0.4 容器手术 + XMP 文本编辑 |
| tif/tiff / arw/nef/nrw/srf/sr2/arq / bmp / gif | **sidecar `.xmp`** | Lightroom 约定；TIFF 走 sidecar 是用户选型（推荐项） |
| EXIF 18246/18249 | **彻底删除** | 读链一并删除，不认存量 |
| 压缩包内 | 会话内存 | 不探测不写入（GIF 等非嵌入格式同样保留会话评级） |

**延迟批量写**：评级按键只进 `App.rating_dirty`（HashMap<PathBuf,u8>，
0=清除语义；压缩包模式不进）；落盘 = 右键菜单「同步评级到文件」+ 退出
**静默自动保存**（无询问弹窗），两者共用 "ratingsync" worker 线程 +
进度窗（无取消按钮）。退出拦截 = eframe 0.36 `close_requested()` +
`CancelClose` 状态机（帧入口 `App::ui` 拦截；Done 收尾 dirty 又非空 →
再启一轮收敛，否则 `ViewportCommand::Close` 放行；`on_exit`/`Drop`
零改动）。**删除文件跳过语义（用户补充定案）**：worker 写前
`path.exists()` 检查，不存在 = 跳过（不算失败、不碰任何文件含残留
sidecar），进度窗三段计数 `N 同步 · K 跳过 · M 失败`；`write_rating`
库函数保持严格（缺失 Err），存在性检查在 worker 层；删除链
（trash 确认执行）同步移除 dirty 防幽灵写。

**选型与关键事实**：

- **img-parts 0.4.2**（纯 Rust 容器手术，`forbid(unsafe)`）：JPEG APP1
  segment / PNG chunk（自动 CRC）/ RIFF WebP 增删改。**无 XML 解析器**，
  XMP 编辑为自写文本手术三件套（`xmp_replace_rating` 原位换值 /
  `xmp_insert_rating` `</rdf:RDF>` 前追加独立 rdf:Description /
  `xmp_strip_rating` 剥离保留其余内容）——不做属性合并、Extended XMP
  段（前缀 `http://ns.adobe.com/xmp/extension/`）天然不误伤；
- **PNG XMP 形态**：iTXt + 关键字 `XML:com.adobe.com.xmp`（XMP 规范
  Part 3，未压缩 flag/method/lang/translated 四 0x00）；
- **WebP 边界（计划假设修正）**：img-parts 内部 `convert_into_infered_kind`
  其实**能自动补 VP8X**（`set_icc_profile`/`set_exif` 副作用路径触发），
  但无干净的公开入口给 XMP 链——定案维持**非 VP8X 显式 Err** 不静默兜底
  （image crate 产出即简单 VP8L，"普通 webp 写入失败"是常态预期）；
- **PNG 方向写回同步改造**：手写 chunk 注入（png_replace_exif_chunk +
  crc32fast）删除 → img-parts `Png::set_exif`（自动插 IHDR 后 + CRC）；
  crc32fast 依赖随之移除；kamadak-exif 收窄到方向读（zip 流内存 buffer
  不可替代）、little_exif 收窄到方向写/tag 编码；
- **配置删键**：`[media] rating_embedded_xmp_enable` 三处删除（serde
  静默忽略旧残留，无迁移）。

**教训**：

1. **手拼 RIFF WebP 测试夹具三连坑**：顶层 chunk id 是 `RIFF`（`WEBP`
   是 List kind）；VP8X 数据块必须 10 字节（flags 1 + reserved 3 + 宽 3 +
   高 3，漏 reserved 3 字节 → image 解码报 InconsistentImageSizes）；
   image crate 的 WebP 编码是 **lossless（VP8L 块）** 非 VP8；
2. **img-parts `JpegSegment::new_with_contents` 超 65533 字节 panic**——
   写链显式检查 APP1 容量上限后 Err，不靠库 panic；
3. XMP 文本手术的双遍结构（元素式成对游标 → 属性式逐处替换）中，
   元素闭标签 `</xmp:Rating>` 内含搜索标记，成对消费保证不漏进属性遍历；
   畸形输入（有开无闭）必须跳出防死循环。

**验证**：`meta::tests` 13 项（矩阵名单/无兜底钉死/文本手术三件套/
jpg-png-webp 嵌入往返+清除幂等+解码完整性/LR 风格包 title 保留/
webp 简单格式 Err 且字节不变/全格式方向写回）；`cargo test` 全量 220
通过；`run_tests.bat` 三段冒烟通过；release 构建通过。手工路径
①-⑧ 见 `.trae/documents/评级子系统重构方案.md`。

## 17.8 评级按需探测（视口惰性，取代 17.6 全量扫描）（2026-11-23）

**动机**：评级的消费者只有列表 ★n 前缀与星级筛选两处，17.6/17.7 的
"打开目录即全量扫"在"翻看几张就关"的主路径上是纯浪费（万级 = 万次
open + 头部读，SSD 3~5s 后台）。用户定案按需探测 + 三条设计约束：
窗口 ≈3×视口且打开即探头部首批；从设计上杜绝队列重复（不做每次调用的
pending 去重）；筛选激活只扫剩余未探测项。

**实现**（`src/ui/open.rs` + `mod.rs` + `panels.rs`，meta.rs 零改动）：

- **mark-at-enqueue 位图去重**：`rating_probed: Vec<bool>`（idx 致密域
  0..entries.len() 下标直寻，零哈希；1 字节/条目）。入队瞬间置位，
  false→true 才真正发送——**标记先于入队**，同一 idx 结构上不可能二次
  入队；无独立 pending 集。单条去重成本 = 一次位图读写，与已标记量无关。
  **位图键 = entry_idx 而非视图行位置**——搜索/筛选/排序只重建 view，
  entries 恒不重排不物理移除（复用"deleted 标记集"既有硬约束，
  ratings 表本身也是 entry_idx 键）；换包 `vec![false; len]` 重新分配；
- **视口钩子 + debounce**：`show_viewport` 闭包内只收集本帧探测窗口
  （绘制范围每侧外扩 vh×(倍数-1)/2，总窗 ≈3×视口）到局部变量，闭包外
  （借中解决 &mut self）判定：窗口与上次已入队窗口比较（每帧一次元组
  比较，没移动零开销）→ 移动记意图窗口 → 意图稳定 200ms 才入队
  （拖动穿越万级行每帧都在变，立即入队 = 结构上全量入队；拖动途中零
  读盘 IO）；**首帧例外：从未入队过（`rating_probe_window` None）立即
  入队**，保住"打开即探首批"不引入 debounce 延迟；
- **常驻 worker**：`"ratingprobe"` 线程 `for batch in cmd_rx` 逐批
  `probe_batch`（纯函数，单测覆盖矩阵分流/名单外零读盘/缺失文件静默
  None），每批回传一条（**空批也发**——inflight 计账需要）；有结果
  request_repaint（空闲全事件驱动）；批次 FIFO，App 侧无可插入的
  pending 队列（瞬拉跳转 = 新批次追加尾部，旧批次残留 ≤ 半窗量级先跑完，
  为 40 条读加优先级不值）；换包 drop job = tx 断连 worker 退出、旧 rx
  随句柄丢弃（迟到结果不串包，无 archive_id 比对）；
- **筛选补扫 + 门控**：下拉激活时 `rating_probe_scan_rest` 遍历打开时
  登记的图片 idx 快照，位图 no-op 天然只入未探测的剩余项（含未读完的
  在途批次也不会重发）；`rebuild_view` 谓词门控从 `rating_scan.is_none()`
  改 **`rating_inflight == 0`**（入队未收齐不生效，收齐由 poll 重建，
  防列表闪变语义不变）；下拉 label 加"（扫描中…）"后缀 + 宽度动态放宽。

**教训**：

1. **HashSet → 位图的演进来自用户对去重成本的追问**：insert 本就是
   O(1) 哈希寻址（不存在"9000 已标记 ×100 入队"的平方成本——那是
   线性扫描去重的形态），但 idx 致密域下位图下标直寻严格更优（零哈希
   + 缓存友好），顺势替换；"去重状态键必须是稳定域"——视图行位置随
   筛选/排序漂移不可作键，entry_idx 由既有硬约束保证稳定；
2. **空批也要回传**：inflight 按批长计账，worker 只发 rated 项会让
   全 None 批的计数永不归还、门控死锁——回传消息必须与命令批一一对应；
3. **首帧立即入队的判定**不能用"probed 空 && inflight==0"（位图按
   entries 分配后永非 empty），改用"从未入队过"（`rating_probe_window`
   is None）——语义等价且 O(1)。
