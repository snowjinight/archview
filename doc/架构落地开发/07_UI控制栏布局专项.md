## 7. UI 控制栏布局专项（五坑 + 字形级测量）

> 机制与不变量见 [ARCHITECTURE §14](../架构设计/14_底部控制栏布局.md)；本节只记踩坑叙事（现象 → 根因 → 修复 → 教训）
> 与测量方法。需求原点：播放键中心恒在窗口水平中线 + 行底到窗口底留隙。

**背景（被否决的两条路，决定了最终方案形态）**：

- 手估像素定位（播放键 = 窗口宽/2 − 按钮宽/2 之类）——用户否决：
  "看看有什么办法可以指定到中线上，而不是通过计算px的方式来做"；
- 每帧计算 + 锚点反馈（读上一帧按钮 rect，下一帧 add_space 补差）——两宗罪：
  逐帧开销（"为了个UI按钮对齐，我需要每帧计算一次？性能有损耗呀"）与反馈环
  （值逐帧收敛/漂移，底部面板被反复推挤，用户实测"底部控制栏会自动往上挤，
  直接挤到顶部"）；
- 最终采纳 egui_alignments 的 **Aligner（sizing-pass 两遍布局）**：egui 生态官方
  路径，首帧隐形测量内容宽 + `request_discard`，次帧按实测精确定位——零手估像素、
  零逐帧反馈计算。后续五坑全部发生在把 Aligner 接进现有面板结构的过程中。

### 7.1 坑1：egui 0.36 `Margin` 字段是 i8

- **现象**：`frame.inner_margin.bottom += 4.0;` 编译报 E0277（期望 i8，遇到 f32）。
- **根因**：0.36 的 `Margin` 四个字段全是 `i8`（内边距语义不需要浮点）。
- **修复**：写整数字面量 `+= 10`（当前底内边距 = 默认 2 + 10 = 12px）。
- **教训**：升级 egui 后，样式/布局类型别按旧肌肉记忆写浮点。

### 7.2 坑2：行尾 `add_space` 垫底——实推 7px 且位置漂移

- **现象**：行尾 `ui.add_space(4.0)` 想给底边留隙，实测行底距窗口底 7px 而非 4，
  且行内元素增减时间距跟着变。
- **根因**：`add_space` 消耗的是**行内剩余空间**，落点取决于行内已分配多少——它没有
  "锚定面板底缘"的语义。真正结构上恒定的间距是面板 frame 的 inner bottom margin：
  bottom 面板锚定窗口底缘 + 行带是面板末元素 ⇒ 行底距窗口底 ≡ margin 值，不随
  内容高度变化。
- **修复**：删行尾 add_space，改 `frame.inner_margin.bottom += 10`（12px）。
- **教训**："留边距"要找结构上恒定的量（面板锚定 + frame margin），不要在流动的
  行内空间上打补丁。这条不变量后来还是"底边距又变窄了"那次排查的裁决依据（见
  7.6 末尾）。

### 7.3 坑3：Aligner 居组 ≠ 居播放键（偏 -28px）

- **现象**：接入 Aligner 后粗看"居中了"，细测播放键中心偏窗口中线 -28px。
- **根因**：Aligner 对齐的是**内容组整体**。按钮组四槽 `[<][播放][>][模式]` 左右
  不对称，组中心 ≠ 播放键中心。
- **修复**：五槽等宽对称 `[隐形48][<][播放][>][模式键48 / 隐形48]`——播放键两侧
  各两槽，播放键恰为组的几何中心，居组 = 居键。图↔视频模式第五槽一实（↻/≡ 模式
  键）一隐（等宽占位），组宽恒定，切模式零位移。
- **教训**："对齐组件"对齐的是它的直接内容矩形；要让某个具体元素落在基准线上，
  必须让该元素处在内容的几何对称位——隐形占位槽是零成本手段。

### 7.4 坑4：自动高度面板 × Aligner 记忆尺寸 = 收缩反馈环

- **现象**：Aligner 版本在图片模式下面板逐帧变矮：实测面板 55→47（压矮 8px）、
  行带从 34 挤到 18、按钮溢出行带绘制。
- **根因**：bottom 面板高度默认自适应内容，而 egui 布局"当帧可用高度"来自**上一帧**
  面板高度；Aligner sizing-pass 又依赖两帧（首帧测量 + `request_discard`，次帧按
  记忆尺寸定位）——两个"看上一帧"的机制互相咬尾：测量帧的可用高度被上一轮记忆
  尺寸压小 → 内容测得更矮 → 面板更矮 → ……逐帧收缩直至内容溢出。
- **修复**：行带高度固定——`allocate_ui_with_layout([可用宽, 34], left_to_right(Min))`
  替代 `ui.horizontal`（后者高度随内容自流）。行高固定后面板总高恒定
  （18 + 34 + frame），反馈环被切断。
- **教训**：任何依赖"上一帧"信息的组件（sizing-pass、记忆尺寸）放进同样依赖
  "上一帧"的自适应容器，都会形成反馈环——解法是在两者耦合路径上放一个**常量**
  （此处即固定行高）。另：行带交叉轴 Min/Center 对子项矩形无影响（子项显式
  34 等高撑满行高），但会继续传导进 Button 内部——那就是坑5。

### 7.5 坑5：Button 文本对齐继承 ui 交叉轴——♪ 字形上移 6px

- **现象**：坑4 修复后 ♪ 音量符号相对**自己的按钮**上移 ~6px（按钮 rect 位置正确、
  纯字形偏上），同行 ▶/< 按钮字形无恙。git 考古：♪ 按钮代码与改动前逐字相同——
  "之前也是同样的UI，改动之后符号就上移了"。
- **根因**（两层）：
  1. egui 0.36 Button 走 AtomLayout，内部文本 `align2` **默认回退到所在 ui 的
     layout 交叉轴**（atom_layout.rs:341：`align2.unwrap_or_else(|| Align2([
     ui.layout().horizontal_align(), ui.layout().vertical_align()]))`）；
  2. 修坑4 时我把音量组交叉轴沿用行带的 Min（`right_to_left(Min)`）→ ♪ 文本在
     34px 按钮内**贴顶**。而 ▶/< 所在的 Aligner 内部恒用
     `Layout::left_to_right(Align::Center)`（aligner.rs:342），交叉轴被钉死
     Center——所以按钮组字形不受外层 Min 污染，这正是"按钮位置对、只有 ♪ 上移"
     的原因。字形级实测（方法见 7.6）：Min 版 ♪墨迹中心比 ▶墨迹中心高 6.0px；
     Center 版（HEAD/修复后）只高 0.5px（两字形本身墨迹差，非布局差）。
- **修复**：音量组交叉轴 Min → Center（`right_to_left(Align::Center)`）。行高已被
  坑4 固定，Center 不会再引发膨胀——膨胀真凶是行带不固定高，不是 Center（当初
  把 Center 一并当元凶去掉属于错误归因，已连带修正 panels.rs / mod.rs 三处注释）。
- **教训**：改 layout 交叉轴的影响不止于子项矩形，还会**穿透 Button 边界**改变其
  内部文本对齐；排查"字形偏移但按钮位置正常"先查所在 ui 的 layout，而不是按钮
  自身参数。Aligner 包裹的内容交叉轴恒 Center，可当"防继承污染"的参照组。

### 7.6 字形级无头测量方法（含两轮回归数据）

**动机**：墨迹中心 vs 按钮中心的差异在 1~6px 量级，截图肉眼比对主观且不可复现，
需要客观、无 GPU、可重复的测量。

**方法**（临时 `examples/vol_geo.rs`，两轮验证后删除）：

1. `Context::default()` + `ctx.run_ui(RawInput { … }, …)` 复刻 mod.rs / panels.rs
   的面板结构（frame margin、seekbar 槽、34px 行带、音量组、五槽组），连跑 4 帧
   ——sizing-pass 次帧才稳定，顺带验帧间稳定性；
2. 字体加载与 app 完全一致（msyh.ttc → `FontData::from_owned` → push 进
   Proportional / Monospace 两族），否则中文字形高度失真；
3. 取 `run_ui` 返回的 `FullOutput.shapes`，过滤 `Shape::Text`，对目标字形（♪/▶）
   拿 `TextShape { pos, galley, .. }`；
4. 对齐量：`galley.rect.translate(pos)` = **文本框**（行高盒）、
   `galley.mesh_bounds.translate(pos)` = **墨迹紧致包围盒**——两者都是 Galley
   公开字段（text_layout_types.rs:736-780）。与按钮 `Response.rect` 对比得：
   文本框中心 − 按钮中心（布局对齐）、墨迹中心差（视觉对齐）。

**第一轮数据（坑5 根因证明，Center vs Min 对比）**：

| 交叉轴 | ♪文本框−♪按钮中心 | ♪墨迹−▶墨迹中心 | ▶墨迹−▶按钮中心 |
|---|---|---|---|
| Center（HEAD / 修复后） | **+0.00** | -0.50 | +1.00 |
| Min（回归版） | **-5.50** | -6.00 | +1.00 |

→ Min 版 ♪ 比 ▶ 整整高 6px（贴顶），▶ 列两行完全相同（Aligner 内部 Center，
不受外层交叉轴影响）——回归 100% 由音量组交叉轴解释，按钮代码无关。

**第二轮数据（12px 终态全量回归，视频/图片两模式 × 4 帧，窗口高 720）**：

| 指标 | 期望 | 视频模式 | 图片模式 |
|---|---|---|---|
| 行底距窗口底 | 12 | [12.0 ×4] | [12.0 ×4] |
| 播放键中心−窗口中线 | 0 | [0.0 ×4] | [0.0 ×4] |
| ♪文本框中心−♪按钮中心 | 0 | [0.0 ×4] | [0.0 ×4] |
| 行底 y（帧间稳定） | 恒定 | [708.0 ×4] | [708.0 ×4] |

**"底边距又变窄了"排查实例**（用户第二次反馈底距问题）：先按 7.2 的不变量分析
（行带是面板末元素 + 面板锚定窗口底缘 ⇒ 间距结构上恒定，内容变化不可能改变它），
再无头实测：Center/Min 两版行带均 680..714，间距恒 6px、无帧间抖动 → 判定**不是
回归**，是当初只加到 6px，视觉上仍显挤；`+= 4` → `+= 10`（12px）后按上表全绿。
**教训**：先分清"值变了"还是"值一直这么小"再动手——机制不变量 + 一次无头实测
即可裁决，避免在错误归因上改代码。

**第三轮数据（模式键 ▶+竖线选形，2026-11-02，examples/icon_geo.rs 测完即删）**：
Hold 图标 "▶❚" 被用户指"竖线上飘"。单 run 内两字形同基线、按钮位置正确——
非布局问题，纯**字形墨迹差/字体回退**：❚ 墨迹中心比 ▶ 高 1.50px（底缘高
2px，肉眼可见）；❙/│/▌/▏ 全为 -1.50（同一回退字体的墨迹带）。改 ▮（Δcy
=0.00、宽 12、高 17≈15）后用户二反馈"不飘了但太宽"，增测细线族：**I
（ASCII）Δcy=-0.50、宽 3、高 14、顶缘与 ▶ 完全齐平（18.50）——定稿
"▶I"**；Ι 同 I（同字体同墨迹）；l -1.50；ASCII "|" +0.50 但高 20、下探
3px 底重；丨（CJK）-0.50、宽 2、高 18（顶缘冒出 2px）。教训：图标混排
异族字形先测墨迹（回退字体的竖线族可能整族偏高）；**对齐之外宽度/高度
也要进指标**——第一轮只看 Δcy 选了 ▮，第二轮才补宽度维度。
