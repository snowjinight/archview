## 1. 大包性能专项修复（Phase 2：27G ZIP / 56G 7z / 万级条目）

> 机制设计（批量解压摊薄、上下游预取、会话化）见 [ARCHITECTURE §11.1/§11.4](../架构设计/11_性能优化与虚拟列表.md)；
> 本节只记事故驱动的修复叙事与坑。

### 1.1 7z folder 直达（最重要的一次修复）

- **现象**：56G 固态 7z 包，解压第 417 个条目（仅一张 JPG）卡 10+ 分钟，CPU 持续满载——表象酷似死循环。
- **根因**：sevenz-rust 的 `SevenZReader::for_each_entries` **从 folder 0 开始顺序解压全部前置 folder**。
  7z 的 folder（固态块）彼此独立，每个 folder 的 pack 流偏移记录在头信息里，但该 API 不利用它。
- **修复**：改用 `BlockDecoder::new(folder_index, ...)` —— 构造时直接 seek 到目标 folder 的 pack 流偏移，
  **前置 folder 只 seek 不解压**。目标即使排在第 4 万个条目，也只需顺序解压其所在 folder 内
  目标之前的少量数据。10 分钟级 → 秒级。
- **教训**：读依赖库源码确认其遍历策略，"能跑通"的 API 路径可能隐含 O(全包) 成本。

### 1.2 ZIP 中央目录逐字段偏移写错

- 中央目录（CD）逐字段偏移曾被写错（compressed/uncompressed size、name/extra/comment length
  共 6 个字段），导致 fast path 全挂、退回慢路径逐条试探——万级条目下就是"打开卡十几分钟"。
  修复后单次顺序读 CD 即完成列表（NAS 随机读 → 顺序读，分钟级 → 秒级）。
- ZIP64 支持：offset/size 超 32 位时的扩展字段解析。

### 1.3 取消机制必须打日志（否则表现为"幽灵并行解压"）

- 取消机制：`Arc<AtomicBool>`。批外跳转的"取消重起"后被解压会话化取代
  （[ARCHITECTURE §11.4](../架构设计/11_性能优化与虚拟列表.md)），cancel 只剩一个用途：切换压缩包时终止解码线程。
- **坑**：所有取消点必须打日志——否则表现为"多条后台解压日志但看不到打断"
  （实际是缓存命中路径丢弃任务却没置 cancel 标志，旧线程静默跑完整个批，
  与新任务并行抢 NAS 带宽）。

### 1.4 行列表虚拟化四坑（每一条都有回归测试钉死）

**机制设计**（三层：行数据缓存一次性构建 / `show_viewport` 只渲染可视行 ±3 /
首帧估算行高 + 实测反馈）见 [ARCHITECTURE §11.2](../架构设计/11_性能优化与虚拟列表.md)。

| 坑 | 现象 | 修复 |
|---|---|---|
| **usize 下溢** | 手动向列表上方滚动再点“下一个” → 列表直接跳到底部。目标行在渲染范围之前时 `pos - range.start` 下溢，debug 下 panic，**release 下 wrap 成 2^64 级天文数字** → 滚动目标被钳到 max_offset | 一切虚拟化下标换算用 `isize` |
| **行高不均匀** | 长文件名自动换行把行撑成 2 行高，首行实测高度被钉在 2 行值上 → 渲染范围按虚高缩水 → 底部空隙 + 翻页时行高双稳态翻转 | 所有列表行 `.truncate()` 强制单行；完整路径走悬停气泡（wid 子窗口时代气泡被 mpv 原生窗口遮挡而禁用，render API 单平面后恢复；目录段琥珀色/文件名主题蓝分色，LayoutJob 单 Label 保证长路径换行正常） |
| **scroll_to_rect 坐标系** | 高亮追踪滚动跳到错误位置。`scroll_to_rect` 接收**屏幕坐标**，而虚拟化闭包内 `max_rect().top()` = 内容顶 + min_row×step，需按此换算目标行 y | 换算公式 `(pos - range.start) × step + 闭包 max_rect().top()` |
| **每帧重算** | 万级条目每帧过滤/排序/clone，UI 帧率跌到个位数 | 行缓存一次性构建；排序预生成小写键再按自然序比较（避免比较器内每次 2 次 to_lowercase 分配）；实测 7-Zip 打包时无视添加顺序强制按字典序写入，故 `ui.sort_files` 默认 false（包内顺序 = 固态包物理码流顺序，预取最优），true = 自然序（数字段按数值 1/2/10）供漫画/图集场景 |
| **行热区 = 文本宽** | egui Button 默认收缩到文本尺寸，短文件名必须点中文字本身才有效（选中/打开/右键全受限） | 行按钮加 `.min_size(vec2(ui.available_width().max(1.0), 0.0))` 抬宽下限到整行：egui `begin_pass` 计算 inner_rect 时已扣除滚动条条带，全宽行不与滚动条重叠（且 hit-test 同层 tie 取后注册者，滚动条在 `ScrollArea::end` 才注册必胜）；高度填 0 保持内容行高，不破坏等高虚拟化前提。点击/双击/Ctrl 点选/右键/悬停气泡走同一 `resp`，扩展后自动全部生效 |

### 1.5 多帧测试方法论

虚拟化 bug 大多是跨帧时序问题（滚轮惯性、动画收敛、行高反馈延迟），
单帧单 pass 的 egui 测试 (`__run_test_ui`) 复现不了。用 `ctx.run_ui(RawInput)` 手动喂
PointerMoved/MouseWheel 事件序列跑 100+ 帧，记录每帧 `ScrollArea::state.offset` 轨迹断言——
上面的 usize 下溢 bug 就是这么先复现再修复的。

### 1.6 上游预取预算收向写反（进度条先满再 skip、锚点前段全没进缓存）

- **现象**：实测 7z 固态包点击未缓存项，"上游预取"进度条先跑满，然后才出现 skip
  （跳过前置）段；批完成后锚点前面的条目一个都没进缓存（列表 ✓ 不亮）。
- **根因**：`compute_batch` 上游预算从 folder 起点**顺向**收（`for i in s..entry_idx`
  攒满即 break）——进批的是离锚点最远的 folder 开头段。而 solid 解码物理序固定为
  skip 前缀 → 上游落盘 → 锚点，进度条于是呈现"上游先满、skip 在后"的倒序；预算被
  folder 开头吃满后，紧贴锚点的高价值段反而没进批。
- **修复**：改为 `(s..entry_idx).rev()` **紧贴锚点反向收**，落盘段 = `[锚点-512MB, 锚点)`
  ——顺序浏览时最可能回看的正是锚点前一段，folder 开头离锚点最远、最先被复用、
  预取价值最低。解码物理序不变，进度条顺序恢复设计意图（skip → 上游落盘 → 锚点）。
- **教训**：solid 流预取批的"收批方向"必须和解码物理序对表——批从物理序哪一端开始
  落地，决定进度条段序与缓存价值分布；组批逻辑改动要用"进度条段序 + 落地清单"实测
  验证（本节与 1.7 都是实测才暴露，单测断言的"批内容"没覆盖"收批方向"语义）。

### 1.7 解压会话批边界真暂停（顺序浏览零前缀续解）

机制设计见 [ARCHITECTURE §11.4](../架构设计/11_性能优化与虚拟列表.md)「批边界真暂停」；
本节记方案取舍与实现细节。

- **现象**：点 100 预取到 299，会话解净退出；顺序浏览 100→299 时每次点击都重启新批
  ——重新找 folder 起点 + skip 重解前缀。解压速度远快于阅读速度，CPU/IO 反复空烧。
- **根因**：`extract_session` targets 解空即 Ok(()) 退出（旧"空闲退出"语义）；
  BlockDecoder 的解码位置不跨轮保留，重启必然重付 folder 前缀。
- **方案取舍**（前两个均被否决）：
  - *顺带落盘*（暂停期间继续解码下游、流经条目落盘）：解压速度 ≫ 阅读速度，缓存会被
    无价值下游淹没，触发 LRU 逐出、把真正要回看的缓存挤掉；
  - *慢速爬行*（限速推进）：爬过的未落盘条目会造成"回头点 miss"，限速实现也复杂；
  - **真暂停**（选定）：纯 sleep——零 CPU、零缓存消耗、解码位置贴着浏览点。
- **实现**（API 约束决定形态）：`for_each_entries` 回调一旦提前返回 Ok(false) 即耗尽、
  无法恢复——真暂停只能在**回调内阻塞**：
  - `pause_at_batch_boundary(session, cancel, folder)`（sevenz_vfs.rs）：50ms 分片睡眠
    轮询 targets/cancel，不持锁睡眠（唤醒延迟 ≤ 一个分片）；cancel → `Err(other("cancelled"))`；
    targets 非空 → `Ok(!other_folder)`（是否跨 folder）；
  - 两个暂停点：解码回调 tgt 分支与非目标分支在"本 folder 解净且整会话无目标"时调用；
    规划期空目标同样驻留等待——原"判空退出"路径整体移除，会话退出只剩 cancel（切包）
    与出错两条路；
  - 唤醒分流：`Ok(true)` = 新目标全在本 folder → 顺流续解，6 个段游标/总量清零（进度
    走 UI 活动指示，下一轮重规划恢复定比）；`Ok(false)` = 新目标在别的 folder → 中断
    回外层重排（focus folder 抢道，跨 folder BlockDecoder 直达）；
  - 解码器与解码位置全程活着——跳到已缓存项 + 下一位未缓存时，续解成本 = 当前位置
    → 新目标，严格优于重启的 folder 从头重解。
- **UI 侧配套**（extract.rs / ui/mod.rs / panels.rs）：
  - **批完成语义拆分**：7z 不再发 `ExtMsg::Done`（线程驻留后"批完成 ≠ 会话退出"）；
    `ExtractJob` 新增 `idle` 标志，FileDone 处理器检测 `pending.is_empty() && !idle`
    置位 + debug 日志 `批完成（会话驻留）`，原 Done 兜底补播逻辑移至此处执行；
    RAR 仍发 Done，由 idle 标志防重；
  - 重定向复用路径清 `j.idle = false`（新批开工）——**漏了它会让新批期间覆盖层不
    显示、下个批完成因 `!j.idle` 不成立而永远检测不到**（文档复查时发现的遗漏，已补）；
  - 去重早退加 `!j.idle` 条件（驻留任务不算"在跑"，entry_idx 停在上批锚点，同位
    重点击照常组批重定向）；
  - 顶栏 idle 时显示"解压会话驻留中"弱标记；覆盖层等待遮罩加 `!j.idle`（驻留期
    不遮画面）；
  - 跳至解压处入口合并进顶栏槽位（"跳至解压处 [n]"按钮，n = 锚点在当前标签页
    的感知序号，不在播锚点即显示；完整文件名与完成与否只在 hover 分流）——原列表
    底部中央与媒体区左下角悬浮按钮均已移除：悬浮版本随列表滚动消失（列表区）或
    遮画面角落（媒体区），顶栏槽位与"后台解压中…/驻留中"标记同位，解压中→完成→
    跳转动线最自然；全屏用 B 快捷键。踩坑：按钮文案曾按 extract_ready 分流（"解压
    完成：xxx｜点击观看"），用户找不到带"跳至解压处"字样的入口；又曾内联完整文件名
    （万级条目长名挤爆顶栏）——入口文案必须含可辨识关键词且只显序号，状态与文件名
    放 hover；
  - 顶栏 mini bar 画**当前活动段**（倒序找第一个 cur>0 且 total>0 的段，2 字段名
    前缀 + hover 精确字节进度）而非固定 Downstream——只画 Downstream 会在跳前置/
    上游预取阶段长时间停 0，用户误以为卡死（实测反馈：跳前置阶段剩余 N 项与进度条
    双双不动，被当成 bug）；
  - mini bar **无比值期兜底显示**（实测踩坑）：定位 `Locate(0,0)`、段骨架 `(0,total)`、
    真暂停唤醒续解（段游标清零后 `(cur,0)`）三种状态画不了比值条，曾整段留白——
    用户下游翻页唤醒续解期间只见"剩余 N 项"不见任何条，误读为"卡在定位"。补
    `ExtractJob.active_phase`（最近一次 Progress 上报段，覆盖语义即当前段）兜底
    显示段名 + spinner；
  - keep / 整窗已落地分支切播放项**不清 j.phases**——进度属于后台解压批，与播放
    切换无关；曾清零导致顶栏 mini bar 每次回看闪一下（消失一帧等下条 Progress
    消息恢复）。同理"剩余 N 项"在跳前置阶段与 keep 串（回看锚点上游已缓存区）中
    恒定也是设计行为：pending 只在条目落地时递减，keep 不碰会话，后台批与 pending
    如实不变，翻页本就不改变它；
  - **空闲不重绘假死（实测踩坑）**：进度消息走通道 + 每帧 try_recv 排空，但 egui
    无输入不产帧——图片浏览一停下，Progress/FileDone 积压无人消费，顶栏冻结在
    最后一帧（下游条满、剩余 N 项恒定、批完成判定不跑），用户当假死；视频常播
    场景 mpv 持续重绘全程掩盖。修复：extract 任务活跃（!idle）时 update 尾部
    `request_repaint_after(100ms)` 定时续帧（驻留/无任务零开销）。教训：**后台
    消息驱动的 UI，必须自己保证帧源**——"每帧 poll"的"每帧"在没有重绘请求时
    根本不存在。
- **RAR 不对称**：unrar processing 遍历无回调内阻塞等价物（会话已免掉线程/通道重建，
  重启重付前缀的成本可接受），保持旧"解净退出 + Done"语义；UI 以 idle 标志兼容
  两种语义。
- **教训**：会话生命周期从"空闲退出"改"驻留"是**协议级变更**——所有依赖"退出"
  做判断的下游（Done 消息、去重早退、覆盖层遮罩、keep 的会话存活要求、顶栏文案）
  要逐一对表，漏一处就是 idle 残留这类隐蔽竞态；回归测试见
  **[DEVLOG §5](05_解压会话化回归测试.md)**。

### 1.8 缓存位图失真（列表显示 ✓ 实际文件不在盘）

- **现象**：实测文件列表显示已缓存（✓），点进去发现文件不在盘上——命中判定指向
  不存在的文件。
- **根因（已定位确认）**：**滞留 FileDone 消息复活已逐出条目**。`ExtMsg::FileDone(i)`
  到达即无条件 `cached[i]=true`，但"rename 成功才发"只保证**发送时刻**文件在，不保证
  **UI 消费时刻**在——`poll_extract` 每帧才排空通道，积压窗口内用户触发新批，
  `evict_if_needed` 删掉刚落地文件（清位循环执行时该位还是 false，滞留消息随后又把
  位写回 true）。放大器：RAR "已存在跳过"路径 metadata 命中即发 file_done，同样有
  发送→消费窗口。次要成因：**双实例共享缓存目录**（vfs/mod.rs 明文支持）——另一实例
  的 evict/clean 删除本实例位图标记的文件，无跨进程通知（外部成因，兜底自愈覆盖）。
- **排查结论**（可排除的方向）：evict 清单完备（仅删除成功且名字可解析才上报，
  aid==id 比对无洞）；archive_id 为路径哈希稳定不变（碰撞只产生假 miss，不产生假✓）；
  scan/写路径全走 ~tmp_+原子 rename 无截断竞态（0 字节条目直写 dest，尺寸恒匹配）；
  clean_on_switch 同 id 重开顺序正确。
- **修复**（两层）：
  - FileDone 置位前 `dest.exists()` 复核（extract.rs）：滞留消息指向已删文件时不再
    置位——根因消除；
  - 命中判定 `dest.exists()` 兜底（`start_extract` 内）：位图命中但文件缺失 →
    `bitmap_miss` 降级未缓存走解压路径，规划块外回写清位 + warn
    `缓存位图失真: [...]（位图命中而磁盘缺失）→ 清位并走解压路径`——覆盖双实例
    共享目录等外部成因，单次失真自愈不累积。开销只在命中路径多一次 exists 系统调用，
    miss 路径（多数）零开销。
- **教训**：跨线程消息里的"事实"只在发送时刻成立——消费侧引用它之前必须与当前
  磁盘状态复核；缓存类位图/索引的信任链再完整也要留一层与磁盘事实核对的兜底，
  位图是判定加速，不是事实本身。

### 1.9 顺序下游浏览触发 folder 前缀重解（8 项漏网 + 缓存免费穿过预算）

- **现象**：实测 7z 固态包（37357 项）顺序下游翻页全程缓存命中，顶栏却出现
  "后台解压中…（剩余 11 项）"+"跳过"进度条，剩余量冻结约 114 秒后才清零——
  用户"连续下游翻动，而且都在缓存中，居然又重新开始从头解压了"。
- **根因**（日志 + 代码交叉验证闭合）：两步叠加。
  1. 批1 上游预算 512MB 从锚点向前收满停在 1165，会话解净 [1165, 2302] 后真暂停
     驻留（解码头停在 2302 之后）；
  2. 用户首次下游翻页（锚点已缓存）触发重定向组批，`compute_batch` 上游收集遇
     缓存条目 `continue` 跳过且**不占预算字节**——缓存区 1165..1945 免费穿过，
     预算零头恰好被 8 个未缓存项 1157..1164 花光收编。这 8 项位于解码头**身后**，
     驻留唤醒顺流续解永远够不着 → 挂 pending 减不掉 → 下游落地后零进展保险触发
     重规划 → solid 流物理约束下只能从 folder pack 起点重解前缀（跳过段 ≈ 114 秒）
     补齐。顺带落盘的前提是解码流"将来还会流过"，收编身后的项违背该前提。
- **修复**（用户参与设计的两条规则 + 一条守卫）：
  - **R1 预算含已缓存项 size**（`compute_batch`，上下游同规则，额度游标与写入量
    分离——写入量仍只计未缓存项供 disk_short/evict 使用）：窗口 = `[锚点-预算,
    锚点+预算]` 随锚点整体滑动，被上一批已解区域的缓存字节顶住，永不越过批起点；
