# §18 IO 调度层接入专项

> 设计与不变量见 [ARCHITECTURE §17](../架构设计/17_IO调度层.md)。
> 本文记录：接入过程、调用方改造清单、测试观察方式变化、踩坑。

## 18.1 背景与决策（2026-11-25）

历史方案是三处手工守卫，规则散落且覆盖不全：

- `extract.rs` 预取：当前张解码中 early-return + 单在途名额（poll 就绪事件
  补发下一个）；
- `compare.rs`：compare_tick 的 window_busy 闸门（窗口栏在途不补发候选）；
- 目录模式评级：**无任何让路**——评级 XMP 随机头读与大图解码在 NAS 正面
  撞（实测 3s 墙钟 vs 1.7s 解码）。

统一为 `src/iosched.rs` 发牌调度器（用户定案键名与默认值）：

| 配置键 | 默认 | 说明 |
|---|---|---|
| `io.io_parallel_max_num` | 1 | Decode 类并行上限，钳制 1..=16；SSD 建议 4~6 |
| `io.prefetch_yield` | true | 解码在途时预取一律推迟 |
| `io.rating_yield` | true | 解码与预取均空闲评级才读下一项 |

调度器只发牌不代理字节；被拒请求由各服务挂 deferred FIFO，完成事件驱动
放行。**串行链与窗口优先不再写代码，是规则涌现**。

## 18.3 记账口径（fail-open 全链）

- `complete` 恒调用 + 饱和下溢（`try_update |n| n.checked_sub(1)`，防双记
  完成 panic）；
- 看门狗剔除回账；迟到消息双记一次完成 → 计数瞬时偏低只多放行（fail-open），
  不卡死；
- 类随消息走：pending 可能被看门狗/invalidate 提前移除，`ImgMsg` 携带 `class`。

## 18.4 测试观察方式变化（重要）

- **串行链测试**（`prefetch_serial_chain_current_first_then_plus1_then_minus1`）：
  断言升级为 deferred 观测——`app.play(1)` 后 ±1 候选
  `is_deferred(k)`（旧版断言"未发起"），就绪链保持不变；
- **对比预取测试**（`compare_prefetch_deferred_until_window_ready`）：窗口栏 1
  可能进 deferred（Decode 预算被栏 0 占住），候选补发后可能排队，断言放宽为
  pending/has/deferred 三态；
- **request 去重测试**：语义钉死——**在途去重优先于 admission**：pending 在途
  时重复 request 被幂等检查吞掉、不进 deferred（初版测试误以为会排队，卡死
  排查后修正，见 18.5）；
- **新增** `probe_batch_评级让路_解码空闲才读`：后台线程跑 probe_batch(Some(&sched))，
  主线程 issue(Decode) 后断言 300ms 不完成，complete 后 join 放行；
- iosched 单测 5 个：admission 矩阵 / 串行链涌现 / complete 饱和下溢 /
  reload 生效与钳制 / can_rating 让路。

## 18.5 踩坑

### 18.5.1 初版测试自摆乌龙：以为"重复请求会排队"

现象：全量测试卡死在 `request_去重与失败事件`（0 CPU 阻塞）。根因：初版
测试断言"第二次重复 request 进 deferred、失败放行时重试出第二条 Failed"——
实际 `request()` 的 **pending 幂等检查在 admission 之前**，重复请求在途时
直接被吞掉（正确语义：不重复排队），失败后 deferred 为空、无第二条事件，
测试 spin 等待永不满足。教训：**幂等去重优先于发牌**是刻意设计（防同一
意图占两个名额），测试观察用 `pending/deferred` 内部状态 + 探针
（`eprintln!` + 单测过滤）定位，不要靠猜。

### 18.5.2 测试预算边界：循环 17 次断言 16 上限

`reload_生效与钳制` 初版 `for _ in 0..17 { assert!(admission); issue; }`——
第 17 次断言时 16 路已在途，admission 必然拒绝。改为 `0..PARALLEL_MAX`
循环 + 循环外断言拒绝。

### 18.5.3 PowerShell 管道缓冲掩盖测试进度

`cargo test | Select-String` / `| Out-File` 输出经 PowerShell 对象管道，
测试卡死时日志为空/不落盘，误判"无输出"。定位手段：`Start-Process` 直接
重定向测试二进制 stderr（libtest 逐行写 stderr，直连文件实时可见）+
`--nocapture` + `eprintln!` 探针 + 测试名过滤缩小范围。

### 18.5.4 并行编辑冲突复发

同一文件多处修改必须逐条串行编辑（历史教训重演）：config.rs 的 IoConfig
结构体定义/字段在早期并行编辑中被静默丢失（DEFAULT_TOML `[io]` 节却幸存），
cargo check 的 E0560/E0433 暴露后补齐。**多编辑同一文件时，每条 Edit 基于
最新文件内容逐条验证。**

## 18.7 调度关键日志（分级口径）

三类观测函数最初只在测试里被调用，非测试构建报 dead_code——接线到日志：

| 级别 | 事件 | 位置 | 内容 |
|---|---|---|---|
| `info` | **IO 排队** | imgview `request`/`request_full`、rawdec 帧与直方图 `request` 的拒绝分支 | 谁、哪类、各类在途计数（`decode_out()`/`prefetch_out()`/`rating_out()`）、队列长度 |
| `info` | **IO 放行** | 三个 deferred 放行 loop pop 后 | 谁 + **排队等待时长**（deferred 条目新增 `at: Instant` 入队时刻） |
| `debug` | IO 开工 | `spawn_base`/`spawn_frame`/`spawn_hist` issue 后 | 类 + 在途计数（直接发牌与放行共用此入口，不与 info 转折重复） |
| `debug` | 预取排队汇总 | extract `prefetch_images` 循环尾（`is_deferred` 接线点） | 本轮候选中被排队等待的数量 |
| `debug` | 评级入队 / 派发 / 收回 | open.rs `rating_probe_enqueue`/`rating_probe_dispatch`/`poll_rating_probe` | 队列长度 + 在途计数（派发链观测） |

分级原则（用户定案）：**info 只打印最重要的信息**（IO 等待的开始与结束两个
转折），更详细的开工/完成细节一律 debug。默认 `log_level = "info"` 下日志
只含排队/放行事件，量级 = 每次让路 2 行，不影响信息密度。

## 18.8 评级并入发牌模型：优先级占槽 + 零轮询（需求升级）

**背景**：初版评级是观察类（worker 读每项前 spin-wait `can_rating()`，
25ms sleep 轮询），用户两点不满——① 并行档（max≥2）评级仍等全空窗口，
扫描饿死；② 轮询/睡眠违反全事件驱动审美。定案模型（用户描述）：

- **优先级占槽**：三类共用 `io_parallel_max_num` 个槽位，槽位算术统一为
  `total < max`（total = 解码+预取+评级在途之和）。评级也是发牌类
  （`IoClass::Rating` 占槽记账 issue/complete）；
- **文件粒度抢占**：阻塞读无法中途打断——在途评级文件读完自然让出，
  **下一项**被派发闸门压住；高优先级请求来了走 admission 排队等槽；
- **最低优先级靠派发顺序**：App 侧评级队列（`rating_queue: VecDeque`）
  在 `poll_rating_probe` 尾部逐条派发，先于它的是三个 deferred 放行 loop；
  `rating_yield` 开启时 deferred 非空不派发（闸门），关闭 = 后台扫旁路
  （槽位照占，不抢已占的槽）；
- **零轮询**：rating worker 改为阻塞收单条命令（`recv` 一条 → 读一个
  文件 → 回一条结果 → `request_repaint` 唤醒 UI），spin-wait/sleep 全删；
  派发链 = 结果回执 + 解码完成事件共同驱动。

**决策记录**：
- `rating_yield` 从 `IoBudget` 移除——admission 保持纯槽位算术，让路语义
  在 App 侧闸门（初版把 yield 判定塞进 admission 导致 `rating_yield=false`
  语义写反：后台扫反而比让路更受限，测试暴露后纠正）；
- 测试观察方式变化：`probe_batch` 函数删除（spin-wait 载体），替代为
  App 级派发测试——`rating_派发_解码占槽等待与记账闭环`（直连通道模拟
  worker 收发）与 `rating_派发_deferred排队让位`（deferred 闸门）；
- 记账变化：inflight 从"按批累加/按批长扣减"改为派发 +1/回执 -1（闭环
  单测钉死）；星级筛选生效条件与"扫描中"百分比同步加 `rating_queue`
  非空判定（队列未派发完 ≠ 扫描完成）；
- 优先级反转免疫的数学依据：派发评级时若槽位有空（`total < max`），
  deferred 必已被放行 loop 清掉（放行 admission 同款算术）——闸门与算术
  双保险，不依赖执行顺序细节。

## 18.9 full 零 IO 门控（用户洞察修正）

**用户观察**：full 升级大多数情况不产生 IO——base worker 的原图已进
natives LRU，full 只是 `build_full` 重采样 + 锐化（纯 CPU，~几百 ms），
只有 natives 未命中（切图回跳/缓存被换/预算逐出）才真读源。

**由此暴露两个问题**：
1. **错门**：旧代码 admission 在 spawn_full 之前、natives 查找在其之后
   ——缓存命中的纯 CPU full 也被 IO 槽门槛拦住排队（预取在途时用户放大
   要白等一场 IO 才开始纯 CPU 重采样）；
2. **记账缺失**：full 只 gate 不占槽——spawn_full 从未 issue，
   FullReady 不回账（仅 FullFailed/看门狗回账，饱和下溢无害但语义错），
   真源读的 full 与预取可在 max=1 下并发。

**修复**（dispatch_full 统一入口，request_full / deferred 放行共用）：
- 先查 natives：命中 → 直接 spawn_full（不发牌不占槽）；
- 未命中 → admission(Decode) → spawn_full 时 issue；
- `ImgMsg::FullReady/FullFailed` 新增 `io: bool` 标志（true=占槽要回账），
  poll 与看门狗按标志回账；`full_pending` 元组加第三项 io 供看门狗对齐；
- 放行 loop Full 分支改走 dispatch_full（命中零槽开工，未命中槽忙保持
  队头）。

**回归测试** `full_原图缓存命中不占槽`：① 未命中占槽→FullFailed 回账
归零；② 命中开工零占槽；③ FullReady{io:false} 不回账。测试坑：
`ImageService::new` 的 orig_budget 传 0（钳到 1）会让 natives 准入按预算
逐出、测试原图推入即逐出，命中路径测不到——预算要给足。

## 18.10 rawdec 记账缺口三连（同款排查）

按 §18.9 的"先 gate 后 issue 是否配对"口径排查 rawdec，发现三处：

1. **Frame 处理器缺回账（死锁级）**：RawFrameService 的 `RawMsg::Frame`
   处理只清 pending 从不 complete——一次 raw 帧软解（对比视图 raw 栏）
   后 Decode 计数永久膨胀，max=1 下**全类 admission 永拒死锁**（deferred
   放行也要过 admission）。imgview 主链路测不到（PNG 目录会话全绿），
   纯潜在雷。
2. **spawn_hist 失败路径缺回账**：直方图 spawn 失败清 pending 落 done
   但不 complete（罕见泄漏）。
3. **两服务无看门狗**：worker 卡死（NAS 巨帧）/消息丢失 → pending 悬挂
   + 计数泄漏永久化。imgview 有 PENDING_TIMEOUT，rawdec 没有。

**修复**：Frame 处理器补 complete；spawn_hist 失败补 complete；两 poll
补看门狗（超时剔除 pending + 回账 + 落确定性失败；imgview 的
PENDING_TIMEOUT 改 pub(crate) 复用）。回归测试
`raw帧解码记账对齐_issue恒回账`：request 占槽 1 → 源缺失 Err 回报 →
poll 回账归零 + errs 落地。

**直方图缓存语义澄清**（用户询问"rawdec 是否也有 LRU"）：
- 相机 RAW / 标准图片的直方图**搭解码便车零 IO**——imgview base worker
  顺手算，随 Ready 消息进 LRU，Ctrl+H 直接取（`img.histogram(key)`）；
- raw dump（mpv 分支）走 HistService 旁路软解——**总是真 IO**（raw dump
  不经过 imgview natives，无缓存可查），占槽语义本来就对，无需改造。

## 18.11 静默进程死亡排查与日志子系统加固（F12 事故）

**现象**：F12 打开 → 打开图片目录（日志洪峰）→ 点击图片播放 → 日志窗
口瞬间消失，之后 F12 永久无响应。用户怀疑"日志池满触发写盘 IO 导致崩"。

**排除**：写盘 IO 恒在独立 flush 线程（5s/64KB 唤醒），`push_bytes` 热
路径纯内存操作（环形 600 行 × 单行截断 1500B 有界）——池满不触发任何
磁盘 IO，假设不成立。

**日志证据**（target/debug/archview.log）：会话 1 最后一条日志后进程
**静默死亡**（下一条"启动"行之间无 panic 痕迹）；会话 2 日志戛然而止
后 9 分钟同进程又响应"打开目录"（半死状态）。根因未定——**panic 输出
（stderr）在 windows 子系统下不可见**，崩溃不留痕迹。

**加固三件**：
1. **panic 钩子**（main.rs）：panic 现场同步直写 archview.log + 环形
   缓冲（`logsink::push_panic`，绕过 5s 批量管线——进程随时终止），
   下次复现即有尸检报告；
2. **logsink 毒化恢复**：全部 `lock().unwrap()` 改
   `PoisonError::into_inner`——任何持锁线程 panic 后日志管线继续工作，
   不 panic 风暴不锁死；
3. **评级日志降级**：派发/收回（每文件一条）debug→trace，info 只留
   批级转折（入队 N 项 + 扫描完成）——千文件目录不再刷屏。

**教训**：windows 子系统下进程死亡默认零痕迹，panic 钩子直写日志文件
是 GUI 程序的必备尸检手段；"日志池满触发 IO"类假设先用管线结构证伪，
再上钩子抓现场。

## 18.12 全链路时序审计（9 项修复，2026-11-25）

**背景**：调度层接入完成后线程交互面扩大（imgdec/rawdec/rawprobe/
ratingprobe/open_archive + 三服务 poll 编排），用户要求全链路重梳时序查
BUG 与持锁卡顿。

**拓扑结论（定性安全）**：三服务全部字段 UI 线程独占，worker 只持
tx/ctx 克隆经 mpsc 回传，**零跨线程共享锁、零持锁卡顿/死锁风险**；
记账闭环（issue ↔ complete）三处 poll 覆盖完整。问题集中在**极端时序
下的记账与状态泄漏**，共 9 项：

| # | 问题 | 根因 | 修复 | 回归测试 |
|---|---|---|---|---|
| 1 | rawdec `retain` 不清 deferred | 死条目驻留 → `deferred_len()` 持续 >0 压死评级让位闸（rating_yield=true 永久饿死评级）+ 对已关栏白做整帧软解 | retain 末尾 `deferred.retain(\|d\| keys.contains(&d.key))`（两服务同款） | `retain_同步过滤deferred死条目` |
| 2 | 换包在途评级漏回账 | 换包 drop job 时 inflight>0 不回补 → `rating_out` 永久 ≥1 → 新会话 admission(Rating) 永假（评级静默失效） | 抽 `rating_probe_session_reset()` 唯一入口：回补 + 8 字段清零 | `rating_换包会话重置_在途回账` |
| 3 | rawdec 看门狗 errs 永久化 | 超时写 errs = "超时≠解码失败"语义错误（NAS 慢读 >10s 大帧是常态，慢文件被永久拉黑） | 超时只 remove+complete；迟到成功消息按 fail-open 回账并落 frames 自愈 | （行为变更，并入既有测试） |
| 4 | deferred 队头优先级反转 | 解码完成瞬间队首陈旧预取先于后面的用户 Decode 放行（NAS 秒级可感） | poll 放行改**两遍扫描**：第一遍只放 Decode/Full，第二遍从队首放 Prefetch 垫底 | `deferred_两遍放行_预取让位用户请求` |
| 5 | HistService Err 无限重试 | 损坏文件每帧重触发 24MP 软解死循环 | 同 contrast 的 Err 也是终态（换 contrast/retain 清理后可重试） | `hist_err终态_不重试` |
| 6 | 评级 send 失败/断连不回账 | dispatch 瞬间 send 失败、poll Disconnected 两路径都漏回账（同 #2 的 rating_out 卡死） | send 失败即时回滚；Disconnected 分支补账 + 摘除 job 防每帧空转 | `rating_send失败_回滚记账` / `rating_worker死亡_poll补账` |
| 7 | spawn_full 覆盖在途 | full_pending 单槽，其它条目派发直接覆盖记账 | dispatch_full 加 busy 守卫：`full_pending.is_some()` 返回 true（受理不抢槽，槽腾出后重触发自然开工） | `dispatch_full_单槽互斥_不覆盖在途` |
| 8 | base 迟到 Ready 旧配置纹理 | invalidate/看门狗剔除后重发的请求，旧 worker 迟到产物按 key 命中新 pending（与 full_epoch 同口径问题） | `base_gen` 代次：spawn_base 捕获随 Ready/Failed 回传，poll **先验再 remove**（误 remove 会吃掉新代次占位） | `迟到ready_代次不符丢弃_新代次落缓存` |
| 9 | iosched 注释失真 | admission doc 写"评级让路在 admission"——实际让路在 App 侧派发闸门 | 注释对齐实现（优先级靠派发顺序，admission 纯槽位算术） | （纯注释） |

**记账回补三态全覆盖**（#2/#6 合并口径，漏任一 = 评级静默失效）：
send 失败回滚（派发瞬间）→ Disconnected 补账（poll 收尽后）→ 换包
会话重置就地回补。

### 18.12.1 踩坑：两遍扫描的双重递增（回归测试抓出）

#4 两遍扫描初版在 Prefetch 跳过分支里写 `i += 1`，随后落入循环底部的
统一 `i += 1`——**双重递增跳过紧随其后的 Decode/Full 条目**：
`[Prefetch, Decode]` 时 Decode 在第一遍根本不被检查，被第二遍队首
Prefetch 抢先放行，优先级反转原样复发。修复 = 空分支留底部统一递增。

**教训**：时序类 bug 肉眼审计难以兜底——`i += 1` 写在分支内还是依赖
循环底部，行为差一倍且编译器不报；**每个时序修复必须带确定性回归测试
（直连通道伪造 worker 收发，免真实线程竞态）**，本次 #4 的反转正是
测试首跑暴露的。

### 18.12.2 踩坑：代次先验再 remove

#8 初版写 `pending.remove(&key).is_some_and(|(_,_,g)| g == gen)`——
代次不符时照样 remove，**吃掉新代次请求的占位**，新 worker 结果无处
落地。正确写法：先 `pending.get` 验 gen，相符才 remove。Failed 分支
同款隐患（迟到 Failed 也会无条件 remove）——`ImgMsg::Failed` 同样
补 gen。

## 18.13 二次独立审计：活性缺口两连（pending 移除不回账 + 评级无看门狗，2026-11-25）

§18.12 之后对调度层再做一轮独立审计（动机：§18.12 口径是"消息能到达"
的三态回补，本轮专门排查"消息永远不来 / 没有看门狗对象"的第四态），
发现两个**活性漏洞**（正常路径全绿、卡死场景触发，同 §18.10.1 性质）：

| # | 现象（潜在） | 根因 | 修复 |
|---|---|---|---|
| 1 | `retain`/`invalidate` 移除在途 pending **不回账**：对比窗口滑动/退出对比（`RawFrameService::retain(&[])`）、热重载重放（`ImageService::invalidate`）恰逢解码在途且 worker 卡死（NAS 慢读）时，该 worker 既不在 pending（看门狗扫不到）、回执也因条目被移除后无人等——`decode_out` 永久 ≥1，max=1 下全类 admission 永拒（浏览冻结）。与 §18.12 #1 是同一个 `retain()` 的两半：上轮只修了 deferred 过滤半，pending 不回账半漏了 | 记账闭环设计依赖"迟到消息恒 complete"，但 pending 移除后迟到消息回来虽会 complete（fail-open 平衡），**前提是消息会来**；卡死 worker 消息永不到达，而看门狗只扫已移除的 pending | 移除 pending 时**即时回账**：`RawFrameService::retain` / `HistService::retain` 统计剔除数逐个 `complete(Decode)` + warn 日志；`ImageService::invalidate` 取出 class 后 `complete` + warn。迟到消息双记由饱和下溢吸收（口径现成） |
| 2 | 评级 worker 无看门狗：`meta::read_rating` 是阻塞 `std::fs` 读（≤512KB 头，无超时）。文件粒度抢占的前提是"读会结束"，**单文件卡死（SMB 断连停滞 30~60s+）= 无边界可让**：`rating_out` 占 1，max=1 下 Decode/Prefetch admission 全拒。img/rawdec/hist 三服务都有 10s 看门狗，唯独评级这条线（在 open.rs，不在三服务清单）什么都没有 | §18.10 按三个 poll 扫描补看门狗，评级不在扫描范围；派发闸（deferred 让位）只挡新派发，管不了在途 | `App.rating_inflight_since`（派发成功即记基准；send 失败回滚 / Disconnected / 换包重置三处同步清零）；`poll_rating_probe` 尾部派发前查 watchdog：在途超 `PENDING_TIMEOUT`（10s）无回执 → `complete` + `inflight=0` + **error 日志**，worker 不摘除（读最终返回后迟到结果照常收回合并，派发链自然恢复） |

**日志口径**：本轮起异常路径升级——评级看门狗超时 = `error!`（真实停滞
且冻结浏览）；retain/invalidate 剔除在途 = `warn!`（常见操作携带的记账
修正，量大不至刷屏，且"卡死"本身由看门狗 error 呈现）。

**回归测试 3 个**（同 §18.12.1 教训：确定性伪造，免真实线程）：

- `rating_看门狗超时_回账放行`（open.rs）：直连通道派发 → 基准时间推过
  阈值 → poll 断言回账 + 槽位可用 + 迟到回执 fail-open 收回；
- `invalidate_在途剔除即时回账`（imgview.rs）：直塞 pending + issue →
  invalidate 断言 Decode/Prefetch 两类名额归零；
- `retain_在途剔除即时回账`（rawdec.rs）：窗口内保留不误回账、栏关闭
  剔除回账，帧服务与直方图服务双覆盖。

设计侧同步：§17.4 记账口径补两条（pending 非看门狗移除即时回账 / 评级
看门狗）。

## 18.14 读段串行与解码并行改造（两段分离定版，2026-11-25）

**背景**：用户实测预取反而变慢、2s 翻页击穿（§18.13 修复后的日志复盘：
预取与评级互相让位等待）。根因是**调度模型与设计初衷错位**——调度器本意
是让远程 NAS 的 HDD 大概率连续读（串行化"源读"），但实现把"读+解码"整个
单元串行化：解码 1.7s 期间 NAS 空转、CPU 排队空转，两头都浪费。设计提案
见 [§18 提案文档](../架构设计/18_读段串行与解码并行改造.md)（含背景时序
图 / 消费者全量盘点 C1~C12），三点用户决议后批准：

1. C7 EXIF 头读与解码读合并为一次 IO（实测证实 File 分支确是两次
   round trip：先读 EXIF 头再 `ImageReader::open` 流式解码）；
2. `io_parallel_max_num` **默认保持 1**，只改语义为"排队+读段单元上限"；
3. mpv stream_cb / 解压会话维持豁免不纳管。

**核心改动（读段/解码段两段分离）**：

| 机制 | 内容 |
|---|---|
| 读闸门 I1 | `IoScheduler::io_gate`（全局 Mutex）+ `io_gate_enter()`：所有纳管源读（C1~C7）同一时刻全系统至多一个在飞 → NAS 顺序读；等待超 `GATE_TIMEOUT`(10s) 旁路放行 + error 日志（NAS 断连退化两读并行，不永久冻结） |
| 记账前移 I2 | `complete` 从"回执消息（UI 侧）"前移到"worker 读毕（线程内）"——成功与失败都算；回执消息不再回账；解码段不占槽，CPU 各消费者拿到源字节后并发 |
| io_done 分流 | pending 条目携带 `Arc<AtomicBool>`（worker 读毕置位）：看门狗超时 / retain / invalidate 剔除按"是否还在读段"分流回账（解码段卡死槽已释放，仅剔除）；§18.13 的"移除必回账"口径随之收敛为"读段未毕才回账" |
| 预取并行 | `PREFETCH_MAX_OUT` 1→2：±1 两单元并行（读段仍过闸门 FIFO 串行，+1 先读），解码段各自并行 |
| EXIF 合并 | `decode_image_orient` 拆 `read_source_bytes`（File 分支 `fs::read` 全量预读，一次 IO 拿全方向+解码源）+ `decode_image_bytes`（纯内存）；`decode_raw_preview_path` 块缓存读删除（全量预读对 HDD 顺序读更友好） |
| raw 拆分 | `decode_raw_frame` 拆 `read_frame_bytes`（闸门内：打开+bayer 探测+seek+读帧）/ `convert_frame`（闸门外：bit_shift/色彩转换/contrast LUT/直方图），RawFrameService 与 HistService 共用 |
| 评级闸门 | 评级 worker（C6）读段包闸门，读毕 worker 内回账；回执消息不回账；看门狗/断连/会话重置三处回账口径改 fail-open 双记吸收 |
| 配置注释 | `io_parallel_max_num` 语义改写（排队+读段单元上限，读闸门控制读串行，解码并行不受本值约束） |
| webp 嗅探 | compare 栏动画 webp 嗅探（§18.3.4 顺手项）挪出 UI 线程：`compare_webp_sniff_dispatch/poll` 异步嗅探（读段过闸门、探针类豁免记账），结果缓存会话内复用；构建时假定静态、动画命中异步改判 Unsupported + invalidate 撤销已发解码 |

**回执消息不再记账后的残余双记来源**：仅"看门狗回账后卡死读才完成"一种
（worker 再 complete 一次），饱和下溢吸收（fail-open 多放行一路，不卡死）
——§18.12 的"类随消息走"与"迟到消息恒 complete"口径整体作废。

## 18.15 IO 代理读重构（调度器自读，线程等 buffer，2026-11-26）

**背景**：§18.14 落地后 NAS 实测翻页仍勉强（发牌方案的记账机制散布
四文件、deferred FIFO 三处重复、io_gate 闸门本质是"没有读线程的调度器"
在模拟读线程）。用户定案：**架构代码易读性优先，调度器改为内部直接读
IO、其它线程等 buffer**。设计见 [§19 提案文档](../架构设计/19_IO代理读重构.md)
（含 D1~D8 决策），同日批准同日落地。

**核心改动（一轮拆光 §18.12~§18.14 的记账/deferred/闸门）**：

| 机制 | 内容 |
|---|---|
| 读线程池 D1 | 读线程数 = `io_parallel_max_num`（语义回归本源，默认 1）：读线程按优先级取任务直接执行源读；动态伸缩（超编取任务前自行退出、缺员提交侧补 spawn，reload 即时生效 **+ notify_all**——park 在空队列上的读者不会自行醒来）；`io_gate` Mutex + 20ms 轮询 + GATE_TIMEOUT 旁路整体删除 |
| 优先级队列 D2 | 三条 FIFO（Decode > Prefetch > Rating）+ 单 Condvar；"评级让路/预取让路"从 App 侧派发闸门 + admission 算术变为队列序一行代码；`prefetch_yield`/`rating_yield`/`PREFETCH_MAX_OUT` 三配置删除（IoConfig 只剩 `io_parallel_max_num`） |
| 事件驱动投递 D3/D4 | `IoJob{work, on_done}` 闭包：读毕 on_done 投 Buffer 消息回服务 poll，poll 收到 spawn 纯 CPU 解码 worker；代次不符的迟到 buffer 丢弃 = 取消语义。raw 读段特例：work 内直接 send 携带 bayer 落定 info 的消息（返回值只有 `Vec<u8>` 表达不了），on_done 只处理 Err |
| 记账全拆 D6 | admission/issue/complete/io_done 分流/评级三处 fail-open 回补全部删除；pending 只存 `Instant` 占位（提交瞬间落，排队+在读+解码统一观测），剔除不回账、迟到回执按 gen 校验丢弃；看门狗 = pending 超 10s 剔除可重试 |
| 评级链路 D8 | App 侧派发链（rating_queue/dispatch/inflight/回补）全删：探测以 IoJob 直接提交 Rating 队列，读毕 on_done 回投 `(idx, 星级)`；换包 = `cancel(Rating)` + drop job（迟到结果落空通道不串包）；星级筛选/顶栏扫描判定源统一改 `sched.queued(Rating) > 0` |
| webp 嗅探 | 自建线程改提交 Decode 类小读任务（bool 编码进 Vec<u8> 回投，读失败按静态放行） |
| 看门狗 D5 | 调度器侧：队列非空且超 READ_STALL(10s) 无读毕 → error + spawn 一次性救援读线程执行队首（fail-open 退化两读并行） |

**实施中发现并当场修正的两个设计落地坑**（详见 §19.8）：
pending 占位若在 Buffer 臂提前移除，Ready 臂的代次校验会全灭、纹理
永不落地（占位必须保留到产物落地）；reload 缩编缺 notify_all 时
park 的读者永不退出。

  `invalidate_剔除在途_迟到消息代次丢弃`、`full_原图缓存命中不经调度器`、
  迟到 ready 代次丢弃；deferred 两遍放行测试删除（机制已拆）；
