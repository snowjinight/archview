# §18 IO 调度层接入专项

> 设计与不变量见 [ARCHITECTURE §17](../架构设计/17_IO调度层.md)。
> 本文记录：接入过程、调用方改造清单、测试观察方式变化、踩坑。

## 18.1 背景与决策（2026-11-25）

历史方案是三处手工守卫，规则散落且覆盖不全：

- `extract.rs` 预取：当前张解码中 early-return + 单在途名额（poll 就绪事件
  补发下一个）；
- `compare.rs`：compare_tick 的 window_busy 闸门（窗口栏在途不补发候选）；
- 目录模式评级：**无任何让路**——评级 XMP 随机头读与大图解码在 NAS 正面
  撞（实测 3s 墙钟 vs 1.7s 解码）。

统一为 `src/iosched.rs` 发牌调度器（用户定案键名与默认值）：

| 配置键 | 默认 | 说明 |
|---|---|---|
| `io.io_parallel_max_num` | 1 | Decode 类并行上限，钳制 1..=16；SSD 建议 4~6 |
| `io.prefetch_yield` | true | 解码在途时预取一律推迟 |
| `io.rating_yield` | true | 解码与预取均空闲评级才读下一项 |

调度器只发牌不代理字节；被拒请求由各服务挂 deferred FIFO，完成事件驱动
放行。**串行链与窗口优先不再写代码，是规则涌现**。

## 18.3 记账口径（fail-open 全链）

- `complete` 恒调用 + 饱和下溢（`try_update |n| n.checked_sub(1)`，防双记
  完成 panic）；
- 看门狗剔除回账；迟到消息双记一次完成 → 计数瞬时偏低只多放行（fail-open），
  不卡死；
- 类随消息走：pending 可能被看门狗/invalidate 提前移除，`ImgMsg` 携带 `class`。

## 18.4 测试观察方式变化（重要）

- **串行链测试**（`prefetch_serial_chain_current_first_then_plus1_then_minus1`）：
  断言升级为 deferred 观测——`app.play(1)` 后 ±1 候选
  `is_deferred(k)`（旧版断言"未发起"），就绪链保持不变；
- **对比预取测试**（`compare_prefetch_deferred_until_window_ready`）：窗口栏 1
  可能进 deferred（Decode 预算被栏 0 占住），候选补发后可能排队，断言放宽为
  pending/has/deferred 三态；
- **request 去重测试**：语义钉死——**在途去重优先于 admission**：pending 在途
  时重复 request 被幂等检查吞掉、不进 deferred（初版测试误以为会排队，卡死
  排查后修正，见 18.5）；
- **新增** `probe_batch_评级让路_解码空闲才读`：后台线程跑 probe_batch(Some(&sched))，
  主线程 issue(Decode) 后断言 300ms 不完成，complete 后 join 放行；
- iosched 单测 5 个：admission 矩阵 / 串行链涌现 / complete 饱和下溢 /
  reload 生效与钳制 / can_rating 让路。

## 18.5 踩坑

### 18.5.1 初版测试自摆乌龙：以为"重复请求会排队"

现象：全量测试卡死在 `request_去重与失败事件`（0 CPU 阻塞）。根因：初版
测试断言"第二次重复 request 进 deferred、失败放行时重试出第二条 Failed"——
实际 `request()` 的 **pending 幂等检查在 admission 之前**，重复请求在途时
直接被吞掉（正确语义：不重复排队），失败后 deferred 为空、无第二条事件，
测试 spin 等待永不满足。教训：**幂等去重优先于发牌**是刻意设计（防同一
意图占两个名额），测试观察用 `pending/deferred` 内部状态 + 探针
（`eprintln!` + 单测过滤）定位，不要靠猜。

### 18.5.2 测试预算边界：循环 17 次断言 16 上限

`reload_生效与钳制` 初版 `for _ in 0..17 { assert!(admission); issue; }`——
第 17 次断言时 16 路已在途，admission 必然拒绝。改为 `0..PARALLEL_MAX`
循环 + 循环外断言拒绝。

### 18.5.3 PowerShell 管道缓冲掩盖测试进度

`cargo test | Select-String` / `| Out-File` 输出经 PowerShell 对象管道，
测试卡死时日志为空/不落盘，误判"无输出"。定位手段：`Start-Process` 直接
重定向测试二进制 stderr（libtest 逐行写 stderr，直连文件实时可见）+
`--nocapture` + `eprintln!` 探针 + 测试名过滤缩小范围。

### 18.5.4 并行编辑冲突复发

同一文件多处修改必须逐条串行编辑（历史教训重演）：config.rs 的 IoConfig
结构体定义/字段在早期并行编辑中被静默丢失（DEFAULT_TOML `[io]` 节却幸存），
cargo check 的 E0560/E0433 暴露后补齐。**多编辑同一文件时，每条 Edit 基于
最新文件内容逐条验证。**

## 18.7 调度关键日志（分级口径）

三类观测函数最初只在测试里被调用，非测试构建报 dead_code——接线到日志：

| 级别 | 事件 | 位置 | 内容 |
|---|---|---|---|
| `info` | **IO 排队** | imgview `request`/`request_full`、rawdec 帧与直方图 `request` 的拒绝分支 | 谁、哪类、各类在途计数（`decode_out()`/`prefetch_out()`/`rating_out()`）、队列长度 |
| `info` | **IO 放行** | 三个 deferred 放行 loop pop 后 | 谁 + **排队等待时长**（deferred 条目新增 `at: Instant` 入队时刻） |
| `debug` | IO 开工 | `spawn_base`/`spawn_frame`/`spawn_hist` issue 后 | 类 + 在途计数（直接发牌与放行共用此入口，不与 info 转折重复） |
| `debug` | 预取排队汇总 | extract `prefetch_images` 循环尾（`is_deferred` 接线点） | 本轮候选中被排队等待的数量 |
| `debug` | 评级入队 / 派发 / 收回 | open.rs `rating_probe_enqueue`/`rating_probe_dispatch`/`poll_rating_probe` | 队列长度 + 在途计数（派发链观测） |

分级原则（用户定案）：**info 只打印最重要的信息**（IO 等待的开始与结束两个
转折），更详细的开工/完成细节一律 debug。默认 `log_level = "info"` 下日志
只含排队/放行事件，量级 = 每次让路 2 行，不影响信息密度。

## 18.8 评级并入发牌模型：优先级占槽 + 零轮询（需求升级）

**背景**：初版评级是观察类（worker 读每项前 spin-wait `can_rating()`，
25ms sleep 轮询），用户两点不满——① 并行档（max≥2）评级仍等全空窗口，
扫描饿死；② 轮询/睡眠违反全事件驱动审美。定案模型（用户描述）：

- **优先级占槽**：三类共用 `io_parallel_max_num` 个槽位，槽位算术统一为
  `total < max`（total = 解码+预取+评级在途之和）。评级也是发牌类
  （`IoClass::Rating` 占槽记账 issue/complete）；
- **文件粒度抢占**：阻塞读无法中途打断——在途评级文件读完自然让出，
  **下一项**被派发闸门压住；高优先级请求来了走 admission 排队等槽；
- **最低优先级靠派发顺序**：App 侧评级队列（`rating_queue: VecDeque`）
  在 `poll_rating_probe` 尾部逐条派发，先于它的是三个 deferred 放行 loop；
  `rating_yield` 开启时 deferred 非空不派发（闸门），关闭 = 后台扫旁路
  （槽位照占，不抢已占的槽）；
- **零轮询**：rating worker 改为阻塞收单条命令（`recv` 一条 → 读一个
  文件 → 回一条结果 → `request_repaint` 唤醒 UI），spin-wait/sleep 全删；
  派发链 = 结果回执 + 解码完成事件共同驱动。

**决策记录**：
- `rating_yield` 从 `IoBudget` 移除——admission 保持纯槽位算术，让路语义
  在 App 侧闸门（初版把 yield 判定塞进 admission 导致 `rating_yield=false`
  语义写反：后台扫反而比让路更受限，测试暴露后纠正）；
- 测试观察方式变化：`probe_batch` 函数删除（spin-wait 载体），替代为
  App 级派发测试——`rating_派发_解码占槽等待与记账闭环`（直连通道模拟
  worker 收发）与 `rating_派发_deferred排队让位`（deferred 闸门）；
- 记账变化：inflight 从"按批累加/按批长扣减"改为派发 +1/回执 -1（闭环
  单测钉死）；星级筛选生效条件与"扫描中"百分比同步加 `rating_queue`
  非空判定（队列未派发完 ≠ 扫描完成）；
- 优先级反转免疫的数学依据：派发评级时若槽位有空（`total < max`），
  deferred 必已被放行 loop 清掉（放行 admission 同款算术）——闸门与算术
  双保险，不依赖执行顺序细节。

## 18.9 full 零 IO 门控（用户洞察修正）

**用户观察**：full 升级大多数情况不产生 IO——base worker 的原图已进
natives LRU，full 只是 `build_full` 重采样 + 锐化（纯 CPU，~几百 ms），
只有 natives 未命中（切图回跳/缓存被换/预算逐出）才真读源。

**由此暴露两个问题**：
1. **错门**：旧代码 admission 在 spawn_full 之前、natives 查找在其之后
   ——缓存命中的纯 CPU full 也被 IO 槽门槛拦住排队（预取在途时用户放大
   要白等一场 IO 才开始纯 CPU 重采样）；
2. **记账缺失**：full 只 gate 不占槽——spawn_full 从未 issue，
   FullReady 不回账（仅 FullFailed/看门狗回账，饱和下溢无害但语义错），
   真源读的 full 与预取可在 max=1 下并发。

**修复**（dispatch_full 统一入口，request_full / deferred 放行共用）：
- 先查 natives：命中 → 直接 spawn_full（不发牌不占槽）；
- 未命中 → admission(Decode) → spawn_full 时 issue；
- `ImgMsg::FullReady/FullFailed` 新增 `io: bool` 标志（true=占槽要回账），
  poll 与看门狗按标志回账；`full_pending` 元组加第三项 io 供看门狗对齐；
- 放行 loop Full 分支改走 dispatch_full（命中零槽开工，未命中槽忙保持
  队头）。

**回归测试** `full_原图缓存命中不占槽`：① 未命中占槽→FullFailed 回账
归零；② 命中开工零占槽；③ FullReady{io:false} 不回账。测试坑：
`ImageService::new` 的 orig_budget 传 0（钳到 1）会让 natives 准入按预算
逐出、测试原图推入即逐出，命中路径测不到——预算要给足。

## 18.10 rawdec 记账缺口三连（同款排查）

按 §18.9 的"先 gate 后 issue 是否配对"口径排查 rawdec，发现三处：

1. **Frame 处理器缺回账（死锁级）**：RawFrameService 的 `RawMsg::Frame`
   处理只清 pending 从不 complete——一次 raw 帧软解（对比视图 raw 栏）
   后 Decode 计数永久膨胀，max=1 下**全类 admission 永拒死锁**（deferred
   放行也要过 admission）。imgview 主链路测不到（PNG 目录会话全绿），
   纯潜在雷。
2. **spawn_hist 失败路径缺回账**：直方图 spawn 失败清 pending 落 done
   但不 complete（罕见泄漏）。
3. **两服务无看门狗**：worker 卡死（NAS 巨帧）/消息丢失 → pending 悬挂
   + 计数泄漏永久化。imgview 有 PENDING_TIMEOUT，rawdec 没有。

**修复**：Frame 处理器补 complete；spawn_hist 失败补 complete；两 poll
补看门狗（超时剔除 pending + 回账 + 落确定性失败；imgview 的
PENDING_TIMEOUT 改 pub(crate) 复用）。回归测试
`raw帧解码记账对齐_issue恒回账`：request 占槽 1 → 源缺失 Err 回报 →
poll 回账归零 + errs 落地。

**直方图缓存语义澄清**（用户询问"rawdec 是否也有 LRU"）：
- 相机 RAW / 标准图片的直方图**搭解码便车零 IO**——imgview base worker
  顺手算，随 Ready 消息进 LRU，Ctrl+H 直接取（`img.histogram(key)`）；
- raw dump（mpv 分支）走 HistService 旁路软解——**总是真 IO**（raw dump
  不经过 imgview natives，无缓存可查），占槽语义本来就对，无需改造。

## 18.11 静默进程死亡排查与日志子系统加固（F12 事故）

**现象**：F12 打开 → 打开图片目录（日志洪峰）→ 点击图片播放 → 日志窗
口瞬间消失，之后 F12 永久无响应。用户怀疑"日志池满触发写盘 IO 导致崩"。

**排除**：写盘 IO 恒在独立 flush 线程（5s/64KB 唤醒），`push_bytes` 热
路径纯内存操作（环形 600 行 × 单行截断 1500B 有界）——池满不触发任何
磁盘 IO，假设不成立。

**日志证据**（target/debug/archview.log）：会话 1 最后一条日志后进程
**静默死亡**（下一条"启动"行之间无 panic 痕迹）；会话 2 日志戛然而止
后 9 分钟同进程又响应"打开目录"（半死状态）。根因未定——**panic 输出
（stderr）在 windows 子系统下不可见**，崩溃不留痕迹。

**加固三件**：
1. **panic 钩子**（main.rs）：panic 现场同步直写 archview.log + 环形
   缓冲（`logsink::push_panic`，绕过 5s 批量管线——进程随时终止），
   下次复现即有尸检报告；
2. **logsink 毒化恢复**：全部 `lock().unwrap()` 改
   `PoisonError::into_inner`——任何持锁线程 panic 后日志管线继续工作，
   不 panic 风暴不锁死；
3. **评级日志降级**：派发/收回（每文件一条）debug→trace，info 只留
   批级转折（入队 N 项 + 扫描完成）——千文件目录不再刷屏。

**教训**：windows 子系统下进程死亡默认零痕迹，panic 钩子直写日志文件
是 GUI 程序的必备尸检手段；"日志池满触发 IO"类假设先用管线结构证伪，
再上钩子抓现场。
