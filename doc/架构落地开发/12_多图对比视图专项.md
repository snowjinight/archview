# §12 多图对比视图专项

> 对应架构章节：[ARCHITECTURE §16](../架构设计/16_多图对比视图.md)。
> 本文记动机、实现过程、守卫细节与测试；机制 / 决策 / 不变量在那边。

## 动机

用户需要把包内 2~6 张图（不同作者 / 不同参数的同类图）分栏并排对比，
同步缩放平移逐区域比对。原决策"非标文件都走 MPV"在对比场景失效——mpv
一个 core 只能渲染一路画面，多栏对比要么多实例（重、状态难同步）要么不可行。
排查发现非标 raw dump 本质是"字节序列 → 像素缓冲"的确定性转换（软解已具备：
§8 的转换器、bayer 探测、bit_shift 语义都在），图片纹理直显路径（13.4）本来
就不走 mpv——**两条非 mpv 路径合流后，对比视图统一走 egui 纹理，mpv 完全
不在场**。方案讨论与决策记录见 `PLAN_compare_view.md`（仓库根目录）。

多选入口复用 encode 批量选择的选择集（原为编码服务建立），选择语义零新增。

## 关键实现细节

### 方案 A 几何（纯函数单测钉死）

共享 zoom = 相对各栏 fit 的倍率、共享 center = 归一化图像坐标。屏幕矩形
推导：`p + center*disp = vp.center` → 中心 = `vp.center + (0.5−center)*disp`。
锚点缩放推导：锚点图像坐标 `u = center + delta/disp` 不动 →
`center' = center + delta*(1/db − 1/da)`。disp 按主栏取值，center 是共享量，
各栏自动对齐。这套数学全部抽成纯函数放 compare.rs 顶部，11 个单测逐个钉死
（大图不露边、小图归中、锚点不动、fit 底界落 None、布局映射、滑动吸附等）。

### RawFrameService 线程模型（crate::rawdec）

每请求 spawn 独立 "rawdec" 线程（`catch_unwind` 兜解码 panic，不炸 UI），
`mpsc` 回 UI 线程上传纹理。三个集合分工：

- `frames`：成功帧缓存（ImgKey → 纹理参数），**保留旧帧**——帧游标移动时
  未及解码的栏显示上一帧而非黑屏闪烁；
- `errs`：确定性失败（参数错 / 数据不足），不重试；
- `pending`：在途请求防重。`request` 幂等：pending / 已有帧 / 已 errs 均跳过；
  帧号钳制到 frame_count−1。

会话切换时 `rawdec.retain(shown_keys)` 丢弃离场栏的全部状态（线程产物由
接收端丢弃即自清）。

### bayer 软解

16bit unpacked Bayer 双线性插值：2×2 相位窗口内同色/异色通道按 1/距离²
加权。相位偏移表 `bayer_offsets` 在解码前按排列（RGGB/BGGR/GBRG/GRBG）
预计算（`[[Vec;2];2]` → 每通道 [Vec;2] 的 [x,y] 偏移），避免逐像素分支。
bayer_auto16le 先跑 `extract::resolve_auto_bayer` 探测排列再进固定排列转换。
`shift_u16_le` 与播放路径 stream_cb::ShiftReader 同语义（u16 LE 配对
wrapping_shl），12bit 低对齐数据位移逐位一致。

### source_ready 闸门（防确定性失败污染）

非流式包（7z/RAR）条目未解完时 dest 文件是半截的，此时发起解码必然失败，
且失败会被两个服务**永久记住**（ImageService → img_fallback 不再重试、
RawFrameService → errs 不再重试）。`source_ready`（File 源 metadata len ==
size）在所有解码请求入口过滤：compare_after_change 建栏、
compare_request_raw_frames、compare_tick 自愈重试三处统一过闸。

### 解压会话联动（非流式包对比）

对比会话触发解压的策略：**仅主栏 start_extract**（solid 包 compute_batch
滑窗顺带解出其它栏；single-file 包其它栏显示等待文案）。触发条件在
compare_tick 内收敛：主栏未落地 && 无密码框 && 无错误 && 进度未覆盖
→ start_extract(master)。落地后 compare_tick 的自愈段 filter source_ready
重新发起解码——落地事件不需要显式通知，轮询即可收敛。

### 防播放劫持（三处守卫）

对比与播放互斥，但解压链路完成时会"好心"补播，必须封死：

1. `play()` 顶部：`compare.is_some()` → 清 compare + clear_shown_multi +
   rawdec.retain([])（防御性：正常路径不会在对比态调 play）；
2. `poll_extract` FileDone 自动播放条件加 `&& self.compare.is_none()`；
3. `poll_extract` Done 兜底补播条件加 `&& self.compare.is_none()`。

对比会话自己触发的解压会话，其 FileDone/Done 一律不回播放——退出对比时
exit_compare → play(master) 是唯一回放入口。

### ImageService 多键驻留

单图模式缓存策略假设"同屏只有一张图"，逐出会抖掉旁边栏的纹理。新增
`shown_multi: HashSet<ImgKey>`：set_shown_multi(shown_keys) 后 cache_push
逐出候选跳过集合内键；`frame_ex(key, drop_stale_full)` 替代原 frame 路径——
非主栏传 `drop_stale_full=false`，防 full 高清纹理槽被非主栏请求逐帧顶掉。

### egui 0.36 实测差异（与 §10 的坑同类）

- `FontId::small()` 不存在 → `TextStyle::Small.resolve(ui.style())` 取字号；
- 栏内裁剪绘制用 `ui.painter_at(cell)`（painter 限定在 cell 矩形内）；
- RawFrameService / RawFrameTex 住 crate::rawdec，结构体与字段需
  `pub(crate)`，ui 层（App 字段、panels 取帧）才可访问。

## 踩坑

- **测试断言自己写错**（5 个，代码数学全对）：shift 测试输入字节序错
  （0xABC0 应为 0x0ABC）；nv12 色度全 0 时 G 最大而非最小（BT.601 下
  R/B 同减同色度偏移，G 不动）；pane_image_rect center=(0,0) 期望值算错
  （中心 = vp.center + 0.5×disp，不是 0）；bayer_offsets 用
  `Default::default()` 得到外层空 Vec，索引 panic → 必须
  `std::array::from_fn` 逐元素建 [Vec;2]；grow_window 测试把"无可追加"
  和"正常放大"写进同一 unwrap 断言，自相矛盾 → 拆两个测试。
  教训：**几何/查表类纯函数，先在草稿纸算一遍期望值再写断言**。

## 测试

- 单测：compare.rs 几何 / 布局 / 滑动窗口测试 + rawdec.rs 转换器 / Bayer

## 重构：raw 软解升格媒体层模块（src/rawdec.rs）

初版为单消费者 YAGNI 决策：raw 软解（转换器 + RawFrameService）只被对比
视图消费，按功能内聚放 compare.rs；而真正多消费者的部分（RawLoad 参数
解析、bayer 探测、预设校验）当时已在 extract.rs。评审后按"能力内聚"合并
抽取：extract.rs 的 raw 装载段与 compare.rs 的软解段本就是同一条 raw 媒体
链路，合并成 `src/rawdec.rs`（与 imgview.rs 平级）后模块有两个真实消费者
（mpv 播放路径 + 对比软解路径），UI 层只剩"申请帧 + 收帧"调用。

- 迁移清单：RawLoad + opts()、raw_demux_opts（App 方法改为薄委托
  `crate::rawdec::raw_demux_opts(&self.cfg, …)`，全部调用点与 ui/tests.rs
  零改动）、detect_bayer_layout / resolve_auto_bayer、全部像素转换器、
  soft_decodable / raw_frame_info / RawFrameInfo、RawFrameService /
  decode_raw_frame 及转换器单测随迁；
- 可见性整体从 pub(super) 升 pub(crate)（跨 ui 模块边界）；
- extract.rs 保留 play/poll 链路不变，compare.rs 只剩会话状态 + UI 组合。
- 教训：单消费者时按功能内聚、多消费者时按能力内聚——但两个粒度的判断
  都要在评审时显式说出来并留迁移触发线，而不是默认现状。
