# 18. IO 读段串行与解码并行改造（提案，已实施定版）

> 状态：✅ 已实施（2026-11-25），正式设计并入 [§17.7](17_IO调度层.md)
> （17.7 读段串行与解码并行），落地记录 DEVLOG §18.14。本文档保留为
> 提案过程与背景记录（背景时序图 / 消费者盘点 / 三点用户决议），文中
> "待评审"字样仅指历史状态。
>
> 一句话复述设计意图：**IO 调度器的初衷是让远程 NAS 的 HDD 大概率连续读
> （串行化"源读"），而不是把"读+解码"整个单元串行化——后者让 NAS 在
> 解码期间空转、CPU 在排队期间空转，两头都浪费。**

## 18.1 背景：现状模型违背了设计初衷

### 18.1.1 现状：worker 是"读+解码"融合单元，占槽直到回执

```
发牌槽（io_parallel_max_num=1）的生命周期：
    spawn（issue）──→ [读源 NAS 200ms][解码 CPU 1.7s] ──→ 回执（complete）
                      └────────── 整段占一个槽 ──────────┘
```

后果（2 秒翻页实测，日志 §18.13 复盘）：

```
t0.0    预取(+1) 开工：读0.2s + 解码1.7s（槽被占 1.9s）
t1.25   翻到 N（+1 尚未就绪，等待）
t1.9    +1 就绪。此刻才放行预取(+2)——NAS 在 0.2~1.9s 期间空转
t3.8    +2 就绪
t3.5    翻到 +1 → +2 要再等 0.3s+
```

- **NAS 侧**：读 0.2s、闲 1.7s——连续读的初衷完全没兑现；
- **CPU 侧**：解码串行排队——四核只用了半核；
- **体感**：+1 秒出、+2 卡，2 秒翻页节奏击穿。评级探测又精确卡进
  "解码完毕→下次翻页"的空闲窗占住唯一槽，放大延迟。

### 18.1.2 目标模型：读段与解码段分离

```
读段（IO）：  全局互斥闸门——同一时刻全系统至多一个源读在飞 → NAS 顺序读
解码段（CPU）：不占 IO 槽——读毕立即释放槽位放行下一读，解码并行跑
```

翻页流水线目标时序：

```
t0.0    显示 N → 预取(+1)：读(0.2s，闸门独占) → 读毕释放闸门 → 解码(1.7s)
t0.2    读段空出（此时 +1 还在解码）
t2.0    翻到 +1：秒出（已就绪）→ 预取(+2) 读立即开工（与 +1 的解码并行）
t2.2    +2 读毕 → 解码(+2) 与解码(+1) 并行
t3.9    +2 就绪（用户 t4.0 翻到，零等待）
```

## 18.2 不变量

| # | 不变量 | 保证手段 |
|---|---|---|
| I1 | **IO 统一串行**：所有纳管源读（18.3.1 C1~C7）同一时刻全系统至多一个在飞——NAS HDD 大概率连续读 | 读闸门 `io_gate`（全局 Mutex，读段持有；豁免清单见 18.3.2） |
| I2 | **CPU 并发**：解码段不占 IO 槽——读毕立即释放槽位放行下一读，各消费者拿到源字节后各自并发 | 槽位 release 时机从"回执"提前到"读毕"（worker 内回账） |
| I3 | **优先级不变**：IO 槽排队时 解码 > 预取 > 评级（deferred 让位规则原样） | UI 侧 admission/deferred 机制不动 |

max 语义变化（默认值**保持 1**，用户决议）：从"单元全生命周期串行槽"
变为"**排队+读段单元上限**"——读毕即释放，解码段不受 max 约束。
在飞解码单元的自然上界 ≈ 显示 1 + 预取 2 + full 1 + 对比栏 6 + 直方图 1
≈ 11 个，最坏内存（6 栏 24MP raw 各 72MB 位图 + 源字节）≈ 0.6GB，受 UI
拓扑约束而非调度器；如需硬上限再议 `decode_max_num` 配置（本轮不做）。

## 18.3 IO 消费者全量盘点（IO 负载 / CPU 负载逐项拆分）

> 原则：**IO 统一串行调度（读闸门），CPU 拿到源字节后各自并发**。
> 每个消费者必须明确：读多少（IO load）、算多久（CPU load）、进不进闸门。

### 18.3.1 纳管消费者（进读闸门）

| # | 消费者 | IO 负载（读段） | CPU 负载（解码段） | 现状记账类 | 拆分点 |
|---|---|---|---|---|---|
| C1 | imgview base 解码（当前图 + 预取 ±1） | **整文件**：File 分支流式边读边解 / Stream `read_to_end`，10~20MB+（NAS） | 图片解码 0.2~2s + Lanczos 降采样（重，当前 fuse 在读段里） | Decode / Prefetch | 拆 `read_source_bytes`（见 18.3.3） |
| C2 | imgview full 高清升级 | 同 C1（原图缓存命中 = 零 IO，直接跳闸门） | 解码 + `build_full` Lanczos ×ppp×3（**最重**） | Decode | 同 C1 |
| C3 | RawFrameService 帧软解（对比栏 ×N 栏） | seek + `read_exact(frame_bytes)`，24MP 帧 ≈ 24MB（NAS） | bayer/yuv→RGB 转换 + contrast LUT + **顺手直方图**（O(像素)） | Decode | 拆 `read_frame_bytes` / `convert_frame` |
| C4 | HistService raw 直方图 | 帧字节读（同 C3 读段） | O(像素) 直方图统计（轻） | Decode | 复用 C3 拆分 |
| C5 | bayer 排列探测（`resolve_auto_bayer` / `detect_bayer_layout`） | 首帧采样行 ≤512KB（发生在 C3 读段**之前**，同 worker 串行） | 排列统计（微） | Decode（随 C3） | 并入 C3 的 `read_frame_bytes` |
| C6 | 评级探测（open.rs 评级 worker，串行收命令） | 头读 ≤512KB（NAS） | XMP/EXIF 解析（微） | Rating | `read_rating` 直接包闸门 |
| C7 | EXIF 方向头读（File 分支，imgview.rs:1377 `read_meta_path`） | **现状实测：两次 NAS round trip**——先开文件读 EXIF 头（:1377），再 `ImageReader::open` 流式解码整图（:1379）；Stream 分支已正确（buf 在内存走 `read_meta_bytes`，:1403 零额外 IO） | EXIF 解析（微） | （随 C1，未单独记账） | 拆分后**一次 IO 拿全**：全量预读一次，EXIF 与解码都吃内存 buf——消掉重复打开（用户决议：IO 一次就要拿到方向信息） |

### 18.3.2 豁免消费者（不过闸门，逐项理由）

| # | 消费者 | IO 负载 | 豁免理由 |
|---|---|---|---|
| C8 | 像素探针（`request_probe` → `probe_raw_pixel`） | 3~8B 直读 | 交互延迟优先：过闸门会排在 20MB 整读后面（+200ms+）；读极小，seek 损失可忽略（豁免是既有决策，维持） |
| C9 | mpv stream_cb 视频流式读 | 连续大流量（秒级长读） | 外部租户不纳管（iosched.rs:14 既定）：视频/图片两态互斥，纳管会卡播放；自身已是顺序流 |
| C10 | 解压会话（批量解压） | NAS 连续读 + 本地缓存写 | 外部租户不纳管（既定）：带进度条的用户显式批量任务 |
| C11 | RatingSyncJob（评级同步写） | 批量写 XMP | 用户显式触发 + 进度条；纳管会把读闸门变读写混合闸，复杂度不值 |
| C12 | 本地缓存路径（`cache::dest_path` 的 File 源） | 本地盘整读 | 与 C1 同一代码路径**被动进闸门**：本地读 <50ms，闸门等待被其快速释放，无害（闸门不区分源位置，接受） |

### 18.3.3 融合点拆分方案（纳管消费者读段/解码段分界）

| 读路径 | 融合点 | 拆分方案 |
|---|---|---|
| C1/C2：`decode_image_orient`（imgview.rs:1352） | File 分支 `ImageReader::open` 流式边读边解；Stream 分支 `read_to_end` | 拆出 `read_source_bytes(source) -> Result<Vec<u8>>`：File 改 `fs::read` 全量预读（**顺带吸收 C7 的 EXIF 头读**），Stream 原样；EXIF 解析、RAW 预览拦截、格式识别留解码段（纯内存） |
| C3/C4/C5：`decode_raw_frame`（rawdec.rs:1330） | `open_frame_reader` + seek + `read_exact(frame_bytes)` 与像素转换连在一起 | 拆成 `read_frame_bytes`（闸门内：打开+seek+读+bayer 探测）+ `convert_frame`（闸门外：bit_shift/色彩空间/直方图）；HistService 复用 |

**File 分支全量预读的内存代价**：文件大小 × 在飞单元数（max=2 → 约
2×20MB）——与 Stream 分支现状（本来就 read_to_end）一致，可接受。

### 18.3.4 盘点发现的隐藏问题（本轮顺手修 / 另列）

- **compare 栏 webp 动图嗅探（`webp_animated`/`source_ready`，compare.rs:280）：
  UI 线程同步读 NAS**（`File::open` + 头部 sniff / `fs::metadata`）——打开
  对比栏时 UI 直接卡在 NAS round trip 上。本轮**顺手项**：挪进闸门 + 移出
  UI 线程（复用栏源就绪判定时机）或至少标注；不挪则维持现状并记录。

## 18.4 发牌与记账机制改造

### 18.4.1 槽位生命周期变化（§17.4 记账口径修订）

```
旧：issue(spawn 时) ──────────────── complete(回执消息时，UI 侧)
新：issue(spawn 时) ── complete(worker 读毕时，线程内回账) ── 解码（无槽）── 回执（不再回账）
```

- worker 闭包克隆 `Arc<IoScheduler>`，读毕（**成功与失败都算**）调
  `complete(class)`，随后置位 `io_done` 标志；
- 回执消息处理器（Ready/Failed/Frame/HistDone/FullReady/评级结果）
  **删除 complete 调用**——消息只负责结果落地，不再参与记账；
- 迟到消息 fail-open 双记问题随之消失（消息不回账）；仅剩的双记来源是
  "看门狗回账后读才完成"，由饱和下溢吸收（口径不变）。

### 18.4.2 pending 条目携带 `io_done` 标志（看门狗/回账分流）

每单元 spawn 时创建 `Arc<AtomicBool>` 存进 pending 条目（worker 持克隆，
读毕置 true）。需要回账的判定点全部改为**查标志**：

| 场景 | 旧逻辑 | 新逻辑 |
|---|---|---|
| 看门狗超时（读段卡死） | complete + 移除 | `!io_done` → complete（槽确实被卡死读占着）+ 移除；`io_done`（卡在解码段）→ 仅移除（槽早已释放） |
| retain/invalidate 剔除在途（§18.13 修复） | 无条件 complete | 同上按 `io_done` 分流——解码段被剔除不再误回账（此前是靠迟到消息 fail-open 兜住的多记） |
| spawn 失败 | complete | 不变（worker 未起，读段未开始） |

### 18.4.3 读闸门设计

```rust
// IoScheduler 新增
io_gate: std::sync::Mutex<()>,
pub fn io_gate_enter(&self) -> MutexGuard<'_, ()> { self.io_gate.lock().unwrap() }
```

- worker：`let _g = sched.io_gate_enter(); let bytes = read_source_bytes(...)?;`
  guard drop 即放行——读毕到解码开始的间隙接近零；
- **闸门挂死风险**（NAS 断连，读永不返回）：闸门被卡死 worker 持有，后续
  读全部排队。缓解：`try_lock` 循环 + 超时旁路——等待超过 `PENDING_TIMEOUT`
  强行进读并 warn 日志（fail-open：退化为两读并行，好过永久冻结；
  与今天 max=1 卡死全链相比已是纯改善）；
- 评级 worker 单线程串行收命令，读段过闸门后 `rating_out` 槽位同样在读毕
  回账（下一评级可立即派发，worker 天然串行处理）；`rating_inflight`
  （UI 侧结果收集计数）语义不变。

### 18.4.4 配置语义更新（用户决议：默认值不动 max，只改语义）

- `io_parallel_max_num`：**默认保持 1**。语义从"单元全生命周期串行槽"改为
  "排队+读段单元上限"——HDD/单文件场景下读段串行大概率性能更优，解码段
  的并行由读毕释放自然获得，无需调大本值。注释同步改写；
- `PREFETCH_MAX_OUT`：1→2。预取从"当前张 → +1 → -1 单在途串行链"
  （extract.rs:193）变为"+1/-1 两单元并行、读段仍按 FIFO 过闸门（+1 先读，
  -1 排后）+ 解码并行"。±1 预取的顺序偏好不变，只是不再用单在途钳死解码。

## 18.6 验收标准

1. **翻页流水线**：2s 连续翻页 +2 不卡（日志可见 +2 的读与 +1 的解码时间重叠）；
2. **读段串行**：NAS/慢盘下日志"读进入/读退出"严格配对，无重叠（观测法：
   读段进/出各打一条 trace，时序不交错）；
3. **记账不变量**：槽位计数在"读毕"即回落（日志 `decode=` 数字在解码期间
   为 0），全量测试零失败；
4. **回归**：§18.12/§18.13 的全部记账回归测试在钉 max=1 后原样通过。

## 18.7 明确不做（本轮边界）

- 不改解压会话（批量解压）的 IO 行为——它不在发牌管辖内（§17.1）；
- 不给探针/缩略图等微读过闸门（豁免维持）；
- 不做读段优先级抢占（闸门 FIFO 已够：读段 ≤ 数百 ms，解码 > 预取的
  优先级由 deferred 让位规则在槽位层面保证）。
