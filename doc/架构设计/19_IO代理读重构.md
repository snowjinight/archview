# 19. IO 代理读重构（调度器自读，线程等 buffer）

> 状态：**已实施**（2026-11-26 提案，同日落地；验收 §19.6 除 NAS 实机项外
> 全部达成：cargo test debug+release 各 245 通过 / 0 失败 / 1 ignored，
> 测试数 251 → 245 与预计相符，代码量净减——deferred/记账/派发链拆除
> 远大于读线程池新增）
> 背景：两段分离改造（§17.7 / §18.14）落地后 NAS 实测翻页仍勉强（落地
> 记录与日志复盘见 DEVLOG §18.15），用户定案：**架构代码易读性优先，
> 调度器改为内部直接读 IO、其它线程等 buffer**——拆除散布在三个服务里的
> deferred/记账/io_done 分流机制。

## 19.1 动机：发牌方案的真实账

发牌方案（§17.1 "只发牌不代理字节"）在两段分离落地后暴露的结构性代价：

- **记账机制散布**：issue（UI 发牌）/ complete（worker 读毕回账）/
  io_done 分流（看门狗、retain、invalidate 三处按标志回账）/
  评级三处 fail-open 回补——口径横跨 iosched.rs + imgview.rs +
  rawdec.rs + open.rs 四个文件。§18.12/§18.13/§18.14 三轮共修了
  8 个记账类 BUG，大半是这套散布机制的账；
- **deferred FIFO 三处重复**：imgview/rawdec 各维护自己的
  deferred 队列 + 放行 loop + 幂等去重顺序（"pending 幂等在
  admission 之前"这类顺序细节即踩坑 §18.5.1）；
- **io_gate 闸门是补丁**：读段互斥靠全局 Mutex + 20ms 轮询 +
  超时旁路——本质是"没有读线程的调度器"在模拟读线程。

代理读模型下这一切天然消失：**队列在调度器、串行在调度器、
优先级在调度器**——服务只剩"提交 → 收 buffer → 解码"。

## 19.2 目标模型

```
提交（UI 线程）：  svc.request(...) → sched.submit(任务) 入优先级队列
读段（调度器内）：N 个读线程（io_parallel_max_num）按优先级取任务执行读
交付（事件驱动）：读毕把 buffer 经现有回执通道投回服务 → poll 收到
解码段（worker）：服务 spawn 纯 CPU 解码 worker（无读段、无记账）
```

翻页流水线时序（与 §17.7 目标完全一致，形态更直白）：

```
UI: request(+1) → 队列 → 读线程读(0.5s) → buffer 投回 → spawn 解码(1.9s)
                                  └→ 读线程空闲 → request(+2) 读立即开工
UI poll: 收 buffer → 起解码 worker → 收 Ready → 上纹理
```

**优先级涌现**：读线程每次取任务按 Decode 队列 > Prefetch 队列 >
Rating 队列——评级 82 项压在队列里也不会挡住一次翻页读（旧模型靠
App 侧派发闸门 + rating_yield 达成，新模型是队列序的天然结果）。

## 19.3 设计决策（D1~D8）

### D1 读线程数 = `io_parallel_max_num`（语义回归本源）

- max=1：单读线程，**同一时刻至多一个源读**（HDD 连续读，默认值不变）；
- max=4：4 读线程并行（SSD 用户收益）；
- `io_gate` Mutex + 超时旁路**删除**（被线程池结构替代）；
- **动态伸缩**：读线程每轮取任务前核对目标数——超编自行退出、
  缺员由提交侧补 spawn，reload 即时生效且不打断在途读。

### D2 优先级队列（三条 FIFO，取任务按序）

```rust
struct IoScheduler {
    queues: [Mutex<VecDeque<IoJob>>; 3],   // Decode / Prefetch / Rating
    cond: Condvar,                          // 读线程阻塞等任务
    readers_target: AtomicUsize,            // = io_parallel_max_num
    readers_active: AtomicUsize,
}
```

- 各队列 FIFO 保序（单图串行链"当前张 → +1 → −1"依旧涌现）；
- 取任务顺序 Decode > Prefetch > Rating（I3 不变，机制从
  "App 侧派发顺序 + admission 算术"变为"队列序"一行代码）；
- 提交幂等在**服务侧 pending 检查**（提交前查），队列内不做去重
  （重复提交在服务侧已被 pending/缓存检查挡住）。

### D3 等待 buffer 的形态：事件驱动投递（方案 B）

- request 只**提交任务**（不 spawn worker）；任务闭包里带结果
  回执通道（现有 `ImgMsg`/`RawMsg`/评级通道）；
- 读毕（成功/失败）→ 投 `Buffer{...}` / `ReadFailed{...}` 消息 →
  服务 poll 收到 → spawn 纯 CPU 解码 worker → 现有 Ready/Failed
  回执落地不变；
- 与用户原话"其它线程负责等待 buffer"等价：等待发生在 UI poll 的
  事件驱动层（无阻塞等待、无轮询），且复用现有 gen 代次校验——
  读毕投递时代次不符直接丢弃（取消语义）。

### D4 任务表达：闭包

```rust
pub struct IoJob {
    pub name: String,          // 日志观测（文件名）
    pub class: IoClass,
    pub work: Box<dyn FnOnce() -> Result<Vec<u8>, String> + Send>,
    pub on_done: Box<dyn FnOnce(Result<Vec<u8>, String>) + Send + 'static>,
}
```

- 读闭包捕获 `ImageSource`/raw 参数等，调度器不感知具体读形态
  （`read_source_bytes`/`read_frame_bytes`/`read_rating`/webp 嗅探
  留在各自模块，接口零耦合）；
- `on_done` = 投回执消息 + request_repaint（读线程内执行，极轻）；
- 解码函数（`decode_image_bytes`/`convert_frame`）留在服务侧
  worker——读线程只读，解码段边界清晰。

### D5 读线程卡死看门狗（NAS 断连场景）

读无法中断（`fs::read` 挂死），单读线程卡死 = 读线全停（解码 worker
已拿 buffer 的不受影响）。缓解：

- UI poll 侧调度器看门狗：`last_read_finished` 超 10s 且队列非空
  → error 日志 + **spawn 一次性救援读线程**执行队首任务
  （fail-open 退化两读并行，与旧 GATE_TIMEOUT 旁路同等级）；
- 救援任务由 `readers_active` 对账吸收（救援线程算一名超编读者，
  完成后按动态伸缩规则自行退出）。

### D6 记账机制全拆（本轮核心红利）

| 旧机制 | 新去处 |
|---|---|
| `admission/issue/complete` | **删除**（队列长度即观测 `queued(class)`） |
| `decode_out/prefetch_out/rating_out` | 删除（读线程忙闲即事实） |
| imgview/rawdec `deferred` FIFO + 放行 loop | **删除**（调度器队列就是排队区） |
| `DeferredReq/DeferredKind/DeferredRawFrame/DeferredHist` | 删除 |
| pending 元组 `(t, class, gen, io_done)` | 简化为 `(t, gen)`——pending 语义 = "已提交等 buffer"（幂等/看门狗/invalidate 剔除仍需要） |
| 看门狗按 io_done 分流回账 | 简化为**按 gen 校验丢弃**（无记账可回，剔除只清 pending） |
| `PENDING_TIMEOUT` 看门狗 | 保留：pending 超 10s 剔除 + warn（读卡死场景可重试） |
| full 缓存命中零 IO 门控 | 保留（dispatch_full 先查 natives，命中不提交读任务） |
| 探针 3~8B / mpv / 解压会话豁免 | 不变（不提交调度器） |

### D7 配置瘦身（提议，待用户确认）

| 配置键 | 处置 | 理由 |
|---|---|---|
| `io_parallel_max_num` | **保留**，语义改"读线程数"（1..=16，默认 1） | HDD=1 串行 / SSD 调大 |
| `prefetch_yield` | **删除** | 旧语义"解码在途时预取不占槽"——代理读后解码不占读线程，读线程空闲读预取无损失；优先级队列已保证 Decode 先读 |
| `rating_yield` | **删除** | 旧语义"deferred 非空不派评级"——代理读后评级天然排在两队列之后，让位涌现 |
| `PREFETCH_MAX_OUT`(=2) | **删除**（改服务侧自律） | extract 一次最多发 ±1 两条、compare 候选一次 6 条，提交方天然限量；队列深度不再需要硬上限 |

### D8 评级链路大简化

- 旧：App 侧 `rating_queue` + `poll_rating_probe` 派发闸门（rating_yield/
  admission/单在途）+ 专用 worker 阻塞收命令 + 三处 fail-open 回补
  + 看门狗回账——§18.8 全套；
- 新：目录扫描完成时**一次性提交全部评级任务**进 Rating 队列（82 项
  排队免费），读毕直接 send 现有结果通道 + repaint；
- `rating_queue/rating_probe 派发链/rating_inflight/会话重置回补`
  全删；换包时 `sched.cancel_rating()` 清 Rating 队列；
- 星级筛选生效条件改为"Rating 队列非空则扫描未完成"
  （`sched.queued(Rating) > 0`）。

## 19.5 不变量（§17.8 正式定版）

1. **读段并行度** = `io_parallel_max_num`（读线程数；max=1 时同一时刻
   全系统至多一个源读——NAS HDD 连续读）；
2. **优先级**：读线程取任务 Decode > Prefetch > Rating，各队列 FIFO
   保序；
3. **解码段无调度约束**：buffer 投回后 spawn 的解码 worker 并行度只受
   UI 拓扑约束（§17.7.4 上界 ≈11 不变）；
4. **取消语义**：换上下文 cancel 清队列 + 在途读毕按 gen 丢弃；
5. 调度器持有读线程与队列——删掉它程序失去串行化，回到介质争抢。

## 19.6 验收标准

1. NAS 实机翻页时序与 §17.7 目标一致（+2 读与 +1 解码时间重叠）；
2. 评级扫描（82 项）压队列时翻页读零等待（Decode 队列优先）；
3. 日志口径：入队（info，队列深度）/ 开工（debug）/ 读毕（debug，耗时）
   / 看门狗（warn）；
4. `cargo test` 全量通过（重写后测试数预计 230±）；
5. 代码量净减（deferred/记账/派发链拆除 > 读线程池新增）。

## 19.7 明确不做

- 不做 JPEG 缩减解码（用户决议：**大图绝不降采样，图像质量优先**；
  大图不做 Lanczos 之外的多级缩放）——解码 1.9s 单线程硬成本保留，
  本轮只优化调度形态，解码并行化（如 zune-jpeg 多线程）另立专项再议；
- 解压会话/mpv/探针豁免不动；评级同步写不动。

## 19.8 实施记录（2026-11-26，同日落地）

按 §19.4 清单顺序执行完毕，落地形态与设计的差异点（均为实施中的
细化决策）：

1. **D3 投递形态细化**：raw 帧读段（`read_frame_bytes` 会改写
   `RawFrameInfo` 的 bayer 排列落定值）无法只用 `Vec<u8>` 返回值表达
   ——work 闭包内**直接 send 携带改写后 info 的消息**（`FrameBuffer`/
   `HistMsg::Buffer`），返回 `Ok(Vec::new())` 占位，on_done 只处理 Err。
   同读线程内先 send 后 on_done，无双消息竞态；
2. **pending 语义 = 已提交等产物**：占位在提交瞬间落（排队+在读+解码中
   统一观测），Buffer 臂**不移除** pending（保留到 Ready/Failed 落地——
   实施初期曾在 Buffer 臂提前 remove 导致 Ready 代次校验全灭、纹理
   永不落地，测试当场暴露后修正）；is_deferred 判定自然消失，
   heal/预取幂等跳过只查 `has || is_pending`；
3. **reload 必须 notify_all**：缩编后 park 在空队列上的超编读者不会
   自行醒来复核退出条件（动态伸缩单测当场暴露）；
4. **评级探测**：`RatingProbeJob` 只持结果通道 `(usize, Option<u8>)`
   （tx 克隆随 on_done 在途，rx 不能断连判死——换包 = `cancel(Rating)`
   + drop job，迟到结果落空通道天然不串包）；星级筛选/顶栏扫描标记
   判定源统一改 `sched.queued(Rating) > 0`；
5. **webp 嗅探**：改提交 Decode 类小读任务，结果 bool 编码进
   `Vec<u8>` 首字节回投，读失败按静态处理放行解码（解码侧自会报错）；
6. 测试重写：imgview/rawdec 消息形态代次校验、ui 预取链断言改
   "占位统一观测 + Decode > Prefetch 队列序"、open.rs 评级 6 个旧
   派发链测试收敛为闭环 + 换包重置 2 个、iosched 单测 8 个
   （队列序/取消/动态伸缩/串行/panic 兜底/queued 观测）。
