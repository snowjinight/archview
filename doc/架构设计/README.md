# 架构设计目录

> 目标：打开一个压缩包（RAR / 7Z / ZIP），浏览其中分散在各子目录的视频与图片文件，
> 视频可直接播放（支持拖动进度条 seek），图片可预览（类 HoneyView 体验），无需完整解压。
>
> **配套文档**：[架构落地开发（原 DEVLOG）](../架构落地开发/README.md)——BUG 修复记录、
> 代码实现细节、踩坑点、排查手册。**两个目录职责互斥**：
>
> | | 架构设计（本目录） | 架构落地开发 |
> |---|---|---|
> | 回答的问题 | **为什么这么设计**：机制、决策、数据流、不变量、模块边界 | **具体怎么做的**：修复过程、实现细节、坑在哪、怎么排查 |
> | 记录 | 设计内容本身 | 现象 → 根因 → 修复 → 教训、测试方法 |
> | 不记录 | BUG 修复叙事 / 实现细节 / 踩坑清单 | 宏观机制设计 |

## 维护约定（强制）

**代码需求变更、新增功能、BUG 修复，都要同步更新文档**——但按职责分流，
**本目录只记录架构设计内容**：

- **机制 / 设计决策变化**（数据流、不变量、模块边界、技术选型变了）：
  在已存在的对应小节文档中更新（如解压会话改动 → `11_性能优化与虚拟列表.md`）；
  全新机制 / 新消费者 / 新子系统 → 新增编号顺延的小节文档（如 `16_新模块.md`），
  并回填本 README 目录表与推荐阅读路径；
- **BUG 修复 / 踩坑 / 代码实现细节：一律不进本目录**（不写修复叙事、
  不留踩坑清单、不记模块内部实现）——全部落
  [架构落地开发](../架构落地开发/README.md) 对应专题（无则新增专题）；
  本目录只在设计本身因此变化时改写对应小节的设计描述；
- **需求变更**（行为 / 交互语义变化）：若影响设计定位或交互设计，
  更新本目录对应小节；变更动机与实现过程落架构落地开发；
- **状态类内容**（✅/🔶 阶段表）随代码推进即时更新，不留"已完成却标规划中"的漂移。

一句话：本目录回答"为什么这么设计、边界在哪、不变量是什么"；
"怎么修的、坑在哪、怎么排查、实现细节"一律在架构落地开发目录。
